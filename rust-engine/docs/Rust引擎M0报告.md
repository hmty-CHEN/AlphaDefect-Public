# Rust 引擎 M0 报告：可行性与基线一致率

2026-10-27。方案见 `Rust引擎方案.md`（决策记录第 137 条）。M0 的目的是在动手适配之前，先量出 spire-mentor 规则内核在 v0.111.0 故障机器人 A10 下和真游戏差多少，以及能快多少。

## 一、做了什么

| 部件 | 位置 | 说明 |
|---|---|---|
| 规则内核 | `rust-engine/vendor/` | spire-mentor 的 `sts2-core`、`sts2-content`、`sts2-srchash`（MIT，提交 8786e93），来源与改动见 `vendor/UPSTREAM.md` |
| Rust 引擎进程 | `rust-engine/crates/sts2-serve/` | 标准输入、输出各一行 JSON。M0 只有战斗模式：`reset`（CombatSpec 的角色、进阶、种子、幕、具体遭遇、牌组、遗物、药水、血量、金币；不支持玩家快照）、`step`、`state`、`encounters`、`bench`。状态输出照搬 spire-mentor 的 `sts2-wire/emit/combat.rs` |
| C# 对拍接口 | `engine/Sts2Headless/Engine/StateProbe.cs`，`{"op":"state"}` | 只读，输出规范化战斗状态与候选，不影响训练路径 |
| 对拍脚本 | `rust-engine/tools/rustdiff/combat_diff.py` | 两边同一 CombatSpec 开战，按 C# 候选随机走（可复现），每步比较，记第一个分歧 |

Rust 端开战照 C# `CombatSetup` 的做法：种子字符串原样做 v0.111.0 的 XxHash64 → 建一局（不进 Neow，满血）→ 按 C# 顺序换牌组、获得遗物、加药水、改血量 → 遭遇的怪物组成用按遭遇命名的随机数（总层数取 1），怪物血量用 Niche 流 → 开战。

比较面：玩家血量、最大生命、格挡、能量、能力、充能球（种类、被动值、激发值）、球位数；手牌（含费用）、抽牌堆（有序）、弃牌堆、消耗堆；活着的敌人的血量、最大生命、格挡、能力、攻击意图（单次伤害 × 次数）；战斗是否结束、是否获胜；候选集合。名字统一规范化后比较。

## 二、一致率

故障机器人、进阶 10，随机策略（按 C# 的候选均匀随机选），Rust 认识的 81 种遭遇（三幕全部普通、精英、Boss 战）轮流打，每场打到结束（最多 400 步）。“一致”指整场每一步的比较面都相同。本机跑（2026-10-27，这一批之后大规模对拍改在 A 上跑）。

| 牌组 | 场数 | 一致 | 一致率 |
|---|---|---|---|
| 初始牌组（4 打击、4 防御、Zap、Dualcast、Ascender's Bane） | 2,000 | 1,999 | 99.95% |
| 随机牌组：初始牌组 + 5–15 张随机的故障机器人牌或无色牌（三成升级），0–4 个随机遗物，0–2 瓶药水 | 1,785 | 1,558 | 87.3% |

随机牌组另有 215 场不计：C# 引擎的战斗模式开不了局。原因是获得时要玩家做选择的遗物（Orrery、Gnarled Hammer、Punch Dagger、Cauldron、Kifuda、Dolly's Mirror、Royal Stamp 等），C# 的开战流程不处理这个选择。这是 C# 战斗模式原有的限制，训练的战斗课程用玩家快照开局，不走这条路。

结论：怪物一侧（81 种遭遇的组成、血量、招式、伤害、随机招式的抽签）与随机数流在初始牌组下几乎完全一致，spire-mentor 的 v0.111.0 支持可用；卡牌、遗物、药水一侧还有一成多的分歧，需要在 M1 逐项修。

## 三、分歧分类

随机牌组 227 场分歧，按第一个分歧的位置：

| 类别 | 场数 | 看到的情况 |
|---|---|---|
| 手牌、抽牌堆、弃牌堆不同 | 132 | 某些牌、遗物、药水的效果与游戏不同，或者抽牌、洗牌、生成牌时用的随机数不一致；需要逐个归因 |
| 选牌候选不同：开战时“三选一”给的牌不同 | 约 37 | 战斗内生成随机牌（CombatCardGeneration 流）与游戏不一致，很可能是同一处根因牵连多局，M1 优先查 |
| 选牌候选不同：Rust 多给“确认” | 34 | 已选张数达到下限时，Rust 允许提前确认，我们的 C# 引擎不给。属于决策语义，按方案由适配层照 C# 处理，不是规则错误 |
| 选牌候选不同：C# 要选牌、Rust 直接结算 | 2 | 某张牌的效果在游戏里要玩家选牌，Rust 自动选了 |
| 玩家能力、充能球、格挡、能量、血量 | 16 | 个别规则错误，例如 Rust 多出敏捷、多出 Echo Form、格挡少 6 |
| 敌人血量、格挡、攻击、数量 | 7 | 例如 Living Fog 少召唤一个 Gas Bomb（初始牌组下唯一的分歧也是它） |

有 44 场在第 0 步（开战后的第一个决策）就已不同，多是开战时的遗物、药水效果或上面的“三选一”。

已修一处（`vendor/sts2-core/src/card_effects.rs`）：游戏的 `CardCmd.Upgrade` 跳过不能升级的牌（诅咒、状态牌），Rust 战斗内的升级没有这道检查，Bellows 开局把 Ascender's Bane 也“升级”了。修后原先分歧的两局都已一致。

另有两项比较面之外的差异，不计入一致率，但 M1 编码观测时必须处理：

- **招式名**：Rust 内部的招式状态名有 29 个与游戏不同（如 `INITIAL_SLEEP` 对 `SLEEP_MOVE`、`BUTT` 对 `TACKLE_MOVE`）。观测里的招式记录用游戏的招式 ID，要建对照表；其中 Lagavulin Matriarch 的 `WAKE_UP_MOVE` 对 `STUNNED` 不像只是改名，要核实。
- **非攻击意图**：游戏一个招式可以同时带几个意图（如“攻击 + 防御”“攻击 + 减益”），Rust 每个怪物只记一个主意图，约 76 种组合。攻击的伤害和次数两边一致。观测的意图标志位需要完整的意图列表，要按招式补齐。

## 四、速度

同一台机器（本机），随机策略打一整场，单进程：

| | 开局 | 每步 |
|---|---|---|
| C# 无头引擎（含观测编码与管道往返） | 1.4–18 ms | 0.6–1.7 ms |
| Rust（开局后每步含合法动作枚举；不含状态编码） | 约 2.9 ms | 约 2 µs |

每步快约 300–800 倍；观测编码在 M1 实现后会慢一些，仍应在数十微秒以内。开局反而不比 C# 快：Rust 建局时会生成地图、预抽各幕的房间、洗遗物袋，战斗模式用不到，M1 改为只建战斗需要的部分。搜索时直接复制战斗状态，不需要重新开局。

## 五、M1 的工作项

1. 部署到 A：Rust 引擎与带 `state` 操作的 C# 引擎，之后的大批量对拍都在 A 上跑。
2. 查“三选一”的随机牌生成，再按分歧类别逐个修卡牌、遗物、药水；每修一处用固定语料回归。
3. 适配层：决策语义照 C#（选牌的确认规则、每房间一次取消等）、CombatSpec 的玩家快照、`reseed` / `replay` / `first`。
4. 观测帧编码（格式版本 10）：招式名对照表、完整意图列表、伤害与格挡预览、招式状态机前推、回合结束预演等；对拍升级为逐帧比较。
5. 开局提速。
