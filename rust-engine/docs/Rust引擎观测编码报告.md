# Rust 引擎观测帧编码阶段报告（rust-obs 分支）

任务：在 Rust 引擎进程里实现与 C# 引擎逐字节相同的观测帧编码（格式版本 10），并逐帧对拍。本报告供主会话合并与登记决策记录；需要登记的决定见第六节。

## 一、结论

| 对拍 | 样本 | 状态一致的帧 | 逐字节一致 |
|---|---|---|---|
| 战斗模式，随机牌组（A） | 5,000 场 | 88,242 | 99.08% |
| 战斗模式，随机牌组（本机） | 400 场 | 7,174 | 99.43% |
| 战斗模式，初始牌组（本机） | 200 场 | 3,601 | 99.92% |
| 整局模式，随机打法（A） | 2,000 局 | 95,673 | 98.97% |
| 整局模式，随机打法（本机） | 200 局 | 9,577 | 99.34% |

A 上的两组跑在提交 `019f7f9`（编码提速和批量接口之前）；之后本机复测，一致率不变。

**收尾后（合并 master 之后的第二轮，本机）**：战斗随机牌组 600 场 99.47%（10,809 帧）、初始牌组 200 场 99.97%、整局 300 局 99.63%（14,214 帧）。整局剩下的 52 帧全是规则内核问题（见第四节第 1、4 条），编码层的已全部对上。“状态一致的帧”指状态对拍（combat_diff / run_diff 的比较面）仍一致的步，状态已分歧的步算规则差异，不计入帧的一致率。

每帧编码耗时：战斗帧约 3.2 微秒（Nibbits 随机打法，取 6 次运行的最小值；同一测试里走一步约 2.3 微秒）。提速前约 10 微秒。

## 二、做了什么

**代码位置**

- `rust-engine/crates/sts2-serve/src/obs/`（新目录）：
  - `mod.rs`：帧缓冲 `Frame`、批量 `Batch`、序列化、base64、调试操作（`obs_moves`、`obs_relics`、`obs_choice`、`obs_bench`）。
  - `vocab.rs`：词表（编译时嵌入 `engine/catalog/vocab.txt`），Rust 枚举名按规范化对到游戏的“类别.条目”键，词表外的键计入头部第 14 项。
  - `tables.rs` + `tables.json`：从游戏导出的静态表（卡牌各升级形态的 DynamicVars 与关键字、怪物招式的意图列表与后续状态类型、能力增减益、药水用途与目标、遗物数值）。
  - `combat.rs`：战斗中的编码（生物、能力、招式预告、充能球、各牌堆、遗物、药水、选牌说明、候选与预览、回合结束预演）。
  - `run.rs`：整局模式（战斗外的全局、玩家、牌组、地图、事件、奖励、卡牌奖励、商店、休息处、宝箱、卡包、牌组选牌）。
  - `relics.rs`：遗物的显示数值、是否显示计数、已用完。
  - `moves_alias.rs`：Rust 招式 ID 与游戏招式 ID 对不上的 21 处对照。
- `combat.rs`、`run.rs`、`decision.rs`、`main.rs` 只加不改：`Session` 加两个字段与 `frame` / `frame_into`、`RunSession` 末尾加只读访问块、`Selection::picked`、`main.rs` 加 `frame` 与 `obs_*` 操作分支和整局计步。
- `vendor/sts2-content/src/cards/preview.rs`：把查表部分抽成 `calc_fn`，新增只读的 `calculated_raw`（计算值卡折算修正前的原始值；`calculated_value` 行为不变）。
- C# 端：新增 `engine/Sts2Headless/Engine/ObsTables.cs`（`obs-tables` 命令导出静态表），`Program.cs` 加一个分支。重新生成静态表：`rust-engine/tools/rustdiff/obs_tables.py`。
- 对拍脚本：`rust-engine/tools/rustdiff/frame_diff.py`（`--decks starter|random` 战斗模式，`--decks run` 整局模式）。

**协议**

- `{"op":"frame"}`：当前决策点的帧，返回 `{"ok":true,"frame":"<base64>","missing":[词表外的键]}`。战斗模式和整局模式都支持。
- 候选顺序与 Rust 的 `step` 下标一致，帧里的候选顺序即动作下标，不需要另外的映射。

**批量接口（M4 用）**

`obs::Batch` 按 Python `sts2rl.features.Ragged` 的布局：`headers` [N×18]，`buf.ti/tf/tp/ci/cf` 各段首尾相接，`tok_off`、`cand_off` 为 N+1 个分界。编码器直接往同一组缓冲区追加（`batch.push(|fr| session.frame_into(fr))`，整局为 `obs::run::encode_into`），记录下标相对本帧编号，单帧编码是批量大小为 1 的特例。编码只读状态、不消耗随机数：预览在战斗状态的复制件上算，战斗模式结束帧的战斗结算在 RunManager 的复制件上跑。核对：3,378 帧批量编码与逐帧编码逐字节相同（`obs_bench` 带 `check_batch`），整局用 `obs_run_batch_check` 抽查。

## 三、与 C# 对齐时的主要做法

- **数值预览不取整**：C# 的卡牌预览是 decimal（虚弱下打击为 4.5）。伤害用内核的 `modify_damage_parts` 按有理数算；格挡内核只给取整结果，用两个大基数探出加项与乘数后按 decimal 重算；计算值卡用新增的 `calculated_raw`。预览时把“正在结算的牌”设为被预览的牌，出牌花费设为它当前的费用（附魔、One For All 等按出牌来源判断）。
- **招式预告**：沿用 Rust 的行动状态机前推 3 步，但以游戏的状态机为准：后续状态的类型（招式、条件分支、随机分支）取游戏导出的表；C# 选定下一招时就记进出招记录，内核要等招式打出才记，所以推算时把当前招式补进记录；被打晕（内核强制换到只有“晕眩”意图的招式）在游戏里是临时造的 STUNNED 招式。
- **游戏用卡牌苦痛、内核用能力实现的效果**（Hex、Tangled、Galvanic），以及 Tainted、Bound 的层数，按游戏补到牌上。
- **能力顺序**：内核玩家的能力分在生物和旧式玩家列表两处，按能力 ID（创建先后）排序还原游戏的施加顺序；内核与游戏施加顺序相反的几对（Shackling Potion / Dark Shackles / Crush Under 与力量，Tender 与力量、敏捷）以及进房间时遗物给的能力，按游戏顺序重排。
- **几率**：C# 的问号房几率与药水几率是 float 逐次加减，内核用 f64。在这些格点上 float 的结果与加减路径无关（已穷举验证到 11 步），按内核的值数出步数再用 float 重算。
- **战斗模式结束帧**：C# 结束时已结算战斗（金币到账、药水几率变化、被偷的牌拿掉），在开战时 RunManager 的复制件上走一遍战斗结束流程再输出。
- **事件选项**：C# 的选项数值除 Neow（所给遗物的数值）外都是 0；悬浮提示里的对象按选项固定，用 C# 跑 1,000 局采集出 20 条对照表（`EVENT_HOVER`）。

## 四、剩余分歧

按来源分三类。条目后的数字是 A 上大样本里出现的帧数。

**规则内核的差异（编码层不该绕开，建议转 rust-combat / 主会话）**

1. 战斗中喝 Ambergris 之后回合数不再增加（整局 521 帧，占整局剩余分歧的一半以上）。状态对拍不比较回合数，所以没被发现；回合数会影响 Stone Calendar 等回合相关效果。
2. Entropic Brew 等生成药水后，内核的 `potion_slot_indices` 出现重复栏位，药水的栏位与顺序和游戏不同（战斗 135 + 62 帧）。
3. Vital Spark 给的 Tainted 等苦痛层数，游戏随能力层数上涨，内核只在施加时记一次。编码层已按能力层数补上，但规则本身可能也有差异。
4. 商店库存没走 `modify_merchant_card_creation_results` 钩子：Fresnel Lens 与三个蛋都注册了监听，但生成商店时没人调用，游戏里商店卡上直接显示附魔或升级，内核要到买下时才在加牌钩子里补上（整局 300 局里 1 帧）。编码层不绕开，否则内核修好后会重复附魔。
5. Hand of Greed 击杀得的金币没加上：内核靠宿主注册 `register_player_gold_gain` 回调，sts2-serve 没注册，两种模式下这 20/25 金币都丢了（战斗模式结束帧 3 处）。Gremlin Merc 偷金币后结束帧金币 Rust 多 5–10，疑似同类（5 处，未细查）。

**编码层还没对齐的（数量小，未逐条排查）**

第二轮已修：Punch Off 悬浮对象；事件选项开打的战斗之后房间类型记为战斗房间（RunSession 加只读标记 `obs_event_combat`）；Bone Tea、Ember Tea、Lasting Candy 的显示（整局没记过计数时取内核初始值）；休息处锻造的“能否取消”；奖励界面候选顺序（离开在用药水之前，改了 `run.rs` 的候选生成）；KnowledgeDemon 给的 Disintegration 伤害 6/7/8；不在手牌的牌去掉本回合随机费用（Snecko 类）；Ceremonial Beast 被打掉犁后的通用晕眩招式；Ringing 苦痛。Neow 的 28 个 EVENTOPT 键不在词表里，C# 同样记为词表外（词表没收任何 Ancient 事件的选项键，两边每场头部第 14 项的增量一致）。

剩下（第二轮本机 600 场战斗）：Mimic 等计算值格挡预览（22 帧）；战斗结束帧上 Ornamental Fan、Kusarigama、Letter Opener、Metronome 的计数（16 帧，两边方向不一，像是致命一击那张牌是否计数的时序差异，需游戏源码确认）；Pen Nib 计数差 1（2 帧）；Thinking Ahead 选牌说明的发起者、牌组顺序等零星项。以下为第一轮的记录：

4. 战斗模式：手牌格挡预览（140 帧，含 Mimic 等计算值内核没有实现的牌）、结束帧的金币（123 帧，疑似 Heist 等夺回的金币未在复制件结算里体现）、遗物显示数值（77 帧，主要是随机牌组里遗物计数的少见状态）、Wither 之外随战斗变化的牌面数值、少量能力顺序与选牌说明。
5. 整局模式：战斗中遗物计数与显示（约 200 帧）、可取消的牌组选牌说明的“能否取消”项（39 帧）、事件里打完战斗后的房间类型（内核仍记为事件房间，约 40 帧）、奖励界面“离开”候选的个别情形（15 帧）、事件悬浮对象表没有覆盖的少见选项（如 Slippery Bridge 的 OVERCOME 是随机一张牌）。
6. 头部第 14 项（词表外键数）：游戏的 STUNNED 招式本来就不在词表里，两边一致；个别怪物的晕眩招式名对照还不全（27 帧）。

**按设计不比较的**

- 头部第 12 项（本进程累计胜场）：与进程有关，frame_diff 不比较。整局模式已按战斗胜利累计，战斗模式在 `Session::step` 里累计。
- 头部第 14 项比较的是每场的增量（一个进程连跑多场时，前面场次遇到的键会一直计在里面）。

## 五、性能

提速前每帧约 10 微秒，热点是标准库 SipHash 查表。做法：查表改用 ahash；卡牌词表 ID 与卡牌静态表按枚举序号直接下标；招式名映射与招式词表 ID 缓存；编码器内“对象 → 记录下标”的小表改成线性数组；出牌候选与回合结束预演只算伤害；序列化整块写。现在约 3.2 微秒，其中复制战斗状态（预览用）约 0.7 微秒。剖析用的 perf 是下载 deb 解包在 scratchpad 里的，没装进系统；WSL 下没有硬件计数器，计时取多次运行的最小值。
