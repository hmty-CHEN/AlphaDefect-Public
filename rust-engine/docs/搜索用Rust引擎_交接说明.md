# 搜索用 Rust 引擎：工作量估算与交接说明

2026-10-31 写，交给维护 `rust-engine/` 的会话。内容是对归档版 Rust 引擎（提交 980a9b0，现在原样在 `rust-engine/`）与现在 C# 引擎、搜索工具的核对结果，以及据此的工作量估算。估算没有实测，标了“估算”的数字都是推的。

## 一、用户要什么

用户的原话：“我目前只是希望给我的模型增加一个搜索的工具，相当于一个外置的大脑。我们的具体训练和评测还是用原来的Csharp引擎。”

所以这件事的目标是：**战斗搜索里的推演改在 Rust 上跑**，真实对局（每一步实际落下的动作、最终输赢）仍然在 C# 引擎上。训练、评测、复测都不换引擎。

和决策记录第 211 条的路线（Rust 替换训练引擎：观测补到 18、修完整局分歧、再分叉对照）相比，搜索只需要其中的**战斗部分**。两者的先后由用户定。

## 二、范围

**要做**

- 战斗模式（`mode: "combat"`）开局、按动作重放、`reseed`、走一步、输出观测帧，与 C# 的语义一致。
- 战斗中的观测帧与 C# 格式 18 一致（网络现在的输入）。
- 第二、三幕 Boss 战的规则与 C# 足够一致，包括第三幕连打两个 Boss。
- 搜索工具能把推演交给 Rust 引擎。

**不用做**

- 战斗外的决策：地图、商店、奖励、事件、古神、休息处。归档时回放对拍只走完 62%，挡住的主要是这些地方的分歧，和搜索无关。
- 战斗外才输出的观测字段：路线摘要、出怪池、商店删牌价、问号房概率、奖励页上没领的卡牌奖励、事件选项特征、小游戏格子等。
- 特权特征（`tok_priv`，版本 11 起）。按 `观测格式.md` 第一节，评测、搜索都不请求特权特征，全部为 0。搜索第 0 步诊断也测过，价值头带不带特权输入与推演得分的相关都是 0.922（`研究报告/2026-10-30_战斗搜索方案调查/第0步诊断结果.md`）。
- PyO3。理由见第四节第 4 项。

**做不到的**：直播。实机桥接不传种子，也读不了战斗局面，搜索只能用在无头 C# 引擎上（评测、考卷、复测）。直播要受益，要么把搜索蒸馏回网络，要么另做实机局面导入（调查报告 4.H），都不在这次的范围里。

## 四、工作项与估算

估算按一个会话连续做；两个会话并行（一个做第 2 项，一个做第 1、3 项）可以缩短到约 1 周。

| # | 内容 | 验收 | 估算 |
|---|---|---|---|
| 1 | **连打与开局规格**：`CombatSpec` 加 `NextEncounter`、`PrevEncounter`，第一场赢了以后照 C# 的做法接第二场；观测头部 16、17、24、25 按格式 15 的规则填 | 双 Boss 诊断卷的题在两边开局、打完第一场、开第二场的状态一致 | 半天 |
| 2 | **战斗观测 10 → 18**：只补战斗中会出现的字段（清单见第五节） | `tools/rustdiff/frame_diff.py` 在双 Boss 诊断卷的贪心轨迹上逐帧对拍；全部一致，或者用下面的“等效验收” | 3–5 天 |
| 3 | **Boss 战规则对拍**：用双 Boss 诊断卷 175 题（真实牌组、真实快照），沿贪心轨迹和若干随机打法对拍第二、三幕 Boss，修分歧 | 贪心轨迹逐步一致的题占绝大多数（建议 ≥ 95%），剩下的分歧列清单、写明对搜索的影响 | 2–4 天，长尾不确定 |
| 4 | **搜索后端**：搜索工具开两组引擎，真实对局用 C# 的 `VecEnv`，推演用 `VecEnv(engine="rust")`。请求格式不用改，Rust 从战斗开头重放一百来步也只要约 0.5 ms，所以先不做状态复制和 PyO3。每个要搜的决策先比较两边根局面的帧，不一致就退回 C# 推演并计数 | 根局面不一致率有统计；小题集上 Rust 后端与 C# 后端的改选基本相同 | 1–2 天 |
| 5 | **验收**：用 Rust 后端重跑第 0 步诊断（175 题，×1，第 108,583 版），与 C# 后端的结果配对比较，记录耗时。在 A 上低优先级跑 | 胜率差在误差内（C# 后端为搜索 77、贪心 64）；耗时明显下降 | 半天到 1 天 |

合计：一个会话约 1–2 周（估算）。最不确定的是第 3 项的长尾，以及第 2 项里需要算游戏逻辑结果的字段。

**第 2 项的等效验收（可选，能砍掉长尾）**：不要求所有字段逐字节一致，而是把同一局面的 C# 帧和 Rust 帧分别喂给网络，比较策略分布的 KL 和价值差。不影响输出的罕见字段先放着，列进清单。代价是要另写这个比较工具，而且以后某个罕见字段起作用时不会被发现。用不用，请先问用户。

**能换来什么（估算）**：推演式改选每走一步都要调一次网络，引擎成本没了以后瓶颈在网络推理，预计快 5–20 倍。以后换成每次模拟只调一次网络的树搜索（调查报告 4.B 的 B2），收益更大，那时再考虑存档恢复和 PyO3。

## 六、风险

- **真实牌组 Boss 战的规则一致率不知道。** 98.4% 是随机牌组、各幕遭遇混合的结果；第三幕 Boss 和强构筑可能碰到没覆盖到的牌与遗物。第 3 项要先测再估。
- **规则偏差的后果**：只会让推演略有偏差，真实结果始终在 C# 上，所以不会弄错输赢；但偏差大的局面上搜索可能选错。根局面不一致时退回 C# 推演，可以兜住最坏情况。
- **观测不一致的后果**：网络看到错的输入，推演里的贪心和价值叶子都会偏。这是硬要求，所以第 2 项一定要对拍。
- **算力纪律**：本机只跑小样本，大批量对拍和第 5 项放 A 上，不拖慢 B 的主线训练。

## 七、约束（沿用项目规则）

- Rust 端只能是按反编译代码重写的规则，不含游戏代码或资源；游戏文件和反编译代码不进仓库。
- 与租用机通讯只走 `tools/remote/hosts.sh` 里的方式；不干扰 ddz 项目。
- 每项重要决定写进 `决策记录.md`（写前先查最大编号）。
