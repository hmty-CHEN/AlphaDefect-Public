# Rust 等价引擎方案

2026-10-27。决策记录第 136 条把主要任务转为开发与游戏逻辑等价的 Rust 引擎；本文是分阶段方案，第 137 条记录用户对路线的选择。

## 一、现状

### 1. 我们的 C# 无头引擎

- `engine/Sts2Headless/` 约 4,300 行，用 Harmony 补丁直接跑游戏的 `sts2.dll`，规则全部由游戏代码执行。补丁只做三类事：替换界面（`FakeScreens`、`UiFlows`、`AgentCardSelector`）、在测试模式里走正式分支（`FidelityPatches`）、提速但不改结果（`PerfPatches`、`MapGenPatch`、`DelayPatch`）。所以它就是“真游戏”的参照。
- 协议（`Server.cs`）：标准输入一行 JSON，标准输出 int32 长度 + 二进制帧。操作有 `reset`（`mode` 为 run / combat，可带 `act_start`、`replay`、`reseed`、`first`、`labels`、`snapshots`、`route_summary`）、`step`、`reseed`、`vocab`、`player`、`close`。
- 决策层（`Decision.cs`、`RunSession.cs`）：所有决策都是单选；多选拆成“逐张选 + 确认”；休息处满血屏蔽“休息”；每个房间只给一次取消；失败过的选项不再提供。这些交互语义 Rust 端必须照搬，否则候选集合对不上。
- 观测（`Observation.cs`，格式版本 10）：实体记录 int32[n,5] + float32[n,20] + 特权 float32[n,2]，候选 int32[m,5] + float32[m,8]。里面有不少需要规则引擎才能算出的量：按当前状态算的卡牌伤害与格挡预览、怪物招式状态机往后推 3 步的概率、回合结束充能球预演、本回合最多能打多少伤害（0–1 背包）、事件选项的数值、路线摘要等。
- **主线游戏版本是 v0.111.0**（Steam public-beta，决策记录第 70 条，`Sts2Headless.csproj` 与 `tools/remote/hosts.sh` 的默认值），不是 v0.107.1。本机反编译代码只有 v0.107.1，v0.111.0 还没反编译（游戏程序集在本机 `~/.local/share/sls2/game/v0.111.0/`，可以用已装的 `ilspycmd` 补上）。

### 2. 可用于对拍的素材

| 素材 | 位置 | 规模 | 用途 |
|---|---|---|---|
| 能力测试回放 | 本机 `~/.local/share/sls2/ability_test/v44820/A00–A10/replays/` | 11,000 局，每局约 700 步，每步记了所选候选的下标 `a` 和种子 | 整局对拍：同一 reset 加同一动作序列 |
| 固定考卷 | `~/.local/share/sls2/distill/exam.json` | 512 场第二、三幕 Boss 战，每项是带 `player_snapshot` 的 CombatSpec | 战斗对拍、搜索效果对照 |
| 卡住与报错现场 | 引擎日志里的 `[stuck-detail]` / `[error-detail]`、`stuck.jsonl` | 带 reset 原文与动作序列 | 回归用例 |

### 3. spire-mentor（MIT）

已克隆到临时目录查看（提交 `8786e93`，2026-10-27）。要点：

- `sts2-rs` 是 13 个 crate 的工作区，规则核心 `sts2-core`（约 20 万行）+ `sts2-content`（约 18 万行，全部卡、遗物、药水、能力、怪物、事件）。这两个 crate 不读游戏文件，源码里也没有嵌入游戏数据；工具链 1.99.1 与本机一致，本机 `cargo build --release` 一次通过。
- **已支持 v0.111.0**：`GameVersion` 是运行时参数，与进阶等级一样贯穿引擎，v0.111.0 的差异按版本分支（约 330 处），包括 v0.111.0 新增的故障机器人卡。
- 随机数：`dotnet_rng.rs` 逐行复刻游戏的 `MegaRandom`（Xoshiro256**，Splitmix64 播种；更早版本用的 .NET `System.Random` 也留着），`run_rng_set.rs` 复刻游戏的各命名随机流。同种子与游戏逐步一致是它对拍的前提。
- 对拍方法：C# 无头真游戏与 Rust 同种子、同动作锁步，每个动作后比较规范化状态，按首个分歧分类（抽牌顺序、牌堆去向、手牌费用、玩家血量、怪物状态……）。公布的一致率：铁甲 100%，其他角色 99.4–99.8%，整局 1,232 / 1,250。**这些数字是 v0.107.1 的**；v0.111.0 的一致率没有公布。
- 它的比较面**不含充能球、姿态和意图**，充能球出错要等到连带改变血量才会被发现。对故障机器人来说这是盲区；我们按观测帧逐字节比较，会比它严格。
- 速度：单核每秒约 5.9 万场随机战斗、约 130 万个引擎动作。

## 二、路线选择（已定：甲）

| 路线 | 做法 | 工作量 | 风险 |
|---|---|---|---|
| **甲（建议）** | 以 spire-mentor 的 `sts2-core` + `sts2-content` 为规则内核，固定在某个提交；我们写适配层：决策语义、观测帧编码、词表映射、协议。用我们自己的 C# 引擎按观测帧对拍，发现的规则错误在我们的分支上修 | 适配层估计 6,000–10,000 行 Rust；修规则的量取决于 v0.111.0 故障机器人的实际一致率，M0 先量出来 | 依赖别人 38 万行代码：出问题要读懂它的结构；上游还在快速演进，跟不跟上游要定规矩 |
| 乙 | 从反编译代码自己重写，先故障机器人 A10 战斗 | 只算故障机器人能拿到的卡（约 90 张本角色 + 无色、状态、诅咒）、约 290 个遗物里战斗相关的大部分、约 60 种药水、约 120 种怪物和 270 种能力，保守估计数万行、数月；整局再翻倍 | 慢；所有一致性问题都要自己再踩一遍 |
| 丙 | 路线甲，但训练退回 v0.107.1（spire-mentor 一致率已验证的版本） | 适配层同甲，修规则最少 | 主线要换游戏版本（决策第 70 条的反向操作），v0.111.0 的内容差异（新增 40 项、改动 157 项）要让模型重新适应 |

建议走甲：spire-mentor 已经替我们做完了最耗时的部分，许可是 MIT，内核不含游戏代码和资源，符合“Rust 端只能是根据反编译代码重写的规则”的约束。丙留作退路：如果 M0 量出 v0.111.0 故障机器人的一致率明显不如 v0.107.1，再请用户在“修 v0.111.0”和“退回 v0.107.1”之间选。

### 代码怎么放（已定：复制进本仓库）

1. **（建议）放进本仓库 `rust-engine/`**：`vendor/sts2-core`、`vendor/sts2-content` 原样复制并保留 LICENSE 与来源提交号，我们的改动单独提交、可以逐条追溯；其余 crate（MCTS、PPO、工作台、wasm）不要。好处是租用机部署不依赖 GitHub，改规则方便。
2. 在用户的 GitHub 上 fork，本仓库用 git 依赖固定提交号。跟上游方便，但每次改规则要两个仓库各提交一次。

## 三、分阶段计划

工作量按“我主导编码、用户审阅关键决定”估算，括号里是粗估；M0 结束后按实测一致率重估。

### M0 可行性与基线（2–3 天；2026-10-27 完成，结果见 `Rust引擎M0报告.md`）

- 选定并固定 spire-mentor 提交，按上面的方式放进仓库，`cargo build`、单元测试跑通；补上 v0.111.0 的反编译代码（本机 `ilspycmd`，放在 `~/.local/share/sls2/decompiled/v0.111.0/`，不入库）。
- 做一个最小的 Rust 引擎进程 `sts2-rs-serve`：只支持 `reset mode=combat`（不带 `player_snapshot` 的故障机器人 A10，给定遭遇）和 `step`，先输出一份 JSON 规范化状态（血量、格挡、能量、能力、充能球、四个牌堆的有序牌、怪物血量与招式），还不编码观测帧。
- C# 引擎加一个调试操作 `{"op":"state"}`，输出同一份规范化状态（只读，不改训练路径）。
- 对拍脚本 `rust-engine/tools/rustdiff/`：两边同 reset、随机策略同动作锁步，记录首个分歧。用 A 或本机跑 1,000 场故障机器人 A10 战斗，**量出 v0.111.0 的基线一致率**。
- 测速：同一台机器上 Rust 与 C# 的每步耗时。
- **出口**：基线一致率、首个分歧的分类统计、速度比；据此确定路线甲是否成立、M1 的修复量。

### M1 故障机器人 A10 战斗等价（1–3 周）

- 适配层：CombatSpec 全部字段（含 `player_snapshot`，即游戏存档格式 `SerializablePlayer`）、战斗内全部决策（出牌、药水、丢药水、战斗内选牌的“逐张选 + 确认”）、`reseed`、`replay`、`first`、`vocab`。
- 观测帧编码：按 `Observation.cs` 逐项实现战斗相关部分（全局、生物、能力、卡牌、遗物、药水、充能球、招式、选牌说明、已选的牌，以及候选特征），二进制格式与版本号完全相同，Python 端不用改。
- 对拍升级为**逐帧比较**：每一步比较整个观测帧（排除与进程有关的头部第 12 项“本进程累计胜场”等，逐项列在脚本里），分歧时打印两边差在哪条记录哪一项。语料：考卷 512 场、能力测试回放里切出的战斗片段（C# 先跑到战斗开始、导出玩家快照）、随机策略和当前策略各若干万场。
- **出口**：上述语料逐帧一致率 ≥ 99.5%，剩下的分歧逐条归类登记（“已知分歧”表，写明影响面）。达到后战斗课程（玩家快照开局的 Boss 练习等）可以先换到 Rust 上，见 M3。

### M2 整局等价（2–4 周）

- 地图生成、Neow、奖励界面、卡牌奖励与卡包、事件（含 Crystal Sphere 小游戏）、休息处、商店、宝箱、换幕、`act_start` 中途开局、`snapshots` 附加信息、`route_summary`。
- 对拍语料：能力测试 11,000 局回放（同种子、同动作序列逐帧比较，分歧以后该局停止），加随机策略整局。
- **出口**：A10 整局逐帧一致率 ≥ 99%，分歧登记在案。

### M3 训练换引擎（主目标，1–2 周）

- 分两步换：M1 达标后先换战斗课程，M2 达标后再换整局采集。评测在一段时间内仍用 C# 引擎作准绳。
- 第一步用同一协议的替身进程：`Sts2Env` / `VecEnv` 只换可执行文件路径，训练代码一行不改。
- 第二步做 PyO3 批量接口：一次调用推进 N 局、直接返回拼好的 numpy 数组，省掉进程间通信和逐帧解析（这一步是否需要，看替身进程下 B 的采集是否仍是瓶颈）。
- 上线方式（需用户批准）：先在 A 上开一条 Rust 训练的分叉与主线对照；评测继续用 C# 引擎作准绳；训练中抽 1% 的局在线锁步核对，一致率掉下来就报警。

### M4 搜索（推迟：训练换完引擎、稳定以后再议）

- 战斗状态可以直接复制，搜索不再每次从战斗开头重放；推演次数从几十次提到几千次。
- 叶子估值仍用我们的价值网络：Rust 端攒批，交给 Python 端 GPU 推理（或导出 ONNX 在 Rust 里推理）。
- 目标：考卷上第三幕第二个 Boss 的胜率；进而用搜索结果蒸馏回策略。

### 优先级（2026-10-27 调整，决策记录第 139 条）

目的是把训练从 C# 引擎换到 Rust 引擎，换完以后先继续训练网络的直觉；搜索不是当前要务。所以 M1–M3 只按训练实际走的路径做（整局模式、玩家快照开局的战斗课程、观测帧版本 10、同一协议），搜索用的功能（复制战斗状态、批量推演）推迟到 M4。开发流程由我自定，遇到阻塞自行决断；大批量对拍放在 A 上，本机只跑小样本。

## 四、随机数

- 游戏的随机数是 `MegaCrit.Sts2.Core.Random.Rng`，内部为 `MegaRandom`（Xoshiro256**，见 v0.107.1 反编译的 `MegaRandom.cs`），带调用计数器，可以快进；按名字分成多条流（整局的 `RunRngSet`、玩家的 `PlayerRng`、战斗内的洗牌与怪物 AI 等），每条流有计数器。种子字符串经 `StringHelper.GetDeterministicHashCode` 变成整数。v0.111.0 把整局种子从 uint 改成了 ulong、去掉了 `Rng.Counter`，要按 v0.111.0 的反编译代码核对。
- spire-mentor 已复刻上述发生器与各流；M0 对拍会直接验证同一 CombatSpec 下第一手牌、抽牌顺序与怪物第一招是否相同。
- 我们的 C# 引擎有两处自己的随机数用法，Rust 端要照搬：`CombatSpec` 按种子抽遭遇（流名 `combat_spec_encounter`）；`reseed` 换掉以后的随机数并重洗抽牌堆（`RunSession.Reseed`）。`reseed` 只供搜索使用，严格说只需分布相同；为了能对拍，仍按同样的算法实现。

## 五、验证与长期维护

- 对拍是 Rust 引擎的准绳：任何规则改动都要过回归语料（固定的若干千场战斗与若干百局整局，几分钟跑完）才能提交。
- C# 引擎继续保留，作为参照与评测用；游戏更新时先更新 C# 引擎，再用对拍找出 Rust 端要跟的改动。
- 对拍与开发不占 B：本机或 A 上跑 C# 参照。

## 六、已定事项（2026-10-27，用户逐项选定）

1. 路线甲：以 spire-mentor 的 `sts2-core` + `sts2-content` 为规则内核，按我们的 C# 引擎逐帧对拍；路线丙（退回 v0.107.1）留作退路，需要时再请用户决定。
2. 代码复制进本仓库 `rust-engine/`，保留 LICENSE 与来源提交号，我们的改动单独提交。
3. 对拍：开发时本机小批量，上万场的回归放 A；不占 B。
4. 本机补做 v0.111.0 的反编译，放 `~/.local/share/sls2/decompiled/v0.111.0/`，不入库。
