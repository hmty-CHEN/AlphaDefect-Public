# sts2-sim 战斗搜索服务：协议与测试

2026-11-01。代码：`Server.cs`（进程协议）、`Session.cs`（会话、候选、存取、reseed）、`TempObs.cs`（临时观测编码器）、`ServeTest.cs`（测试）、`serve_smoke.py`（协议冒烟测试）。方案见 `方案.md` 第 5 项。

## 一、启动与帧格式

```
dotnet Sts2SimServe.dll serve [vocab.txt]
```

帧格式与 Sts2Headless 的 `serve` 相同，`python/sts2env/env.py` 的 `_Process` 可以直接读：

- 请求：标准输入一行一个 JSON。
- 响应：标准输出写 `int32 字节数` + 内容。出错时内容为 `int32 −1` + UTF-8 错误信息，进程继续可用。
- 日志只写标准错误。sts2-sim 往标准输出写的内容也改到标准错误，免得弄坏帧。
- `vocab.txt` 只给临时编码器填记录的词表 ID；不给时一律为 0。

## 二、请求

| 请求 | 回应 | 说明 |
|---|---|---|
| `{"op":"reset","mode":"transplant","save":{…},"next_room_id":n,"target":[列,行],"room":"monster\|elite\|boss"}` | 第一个决策的帧 | `save` 与 `next_room_id` 就是真实引擎 `save` 操作的回应（游戏自己的整局存档 + 下一个房间编号）；`target` 是要进的格子。流程同 `Check.cs`：`NativeSave.ToSnapshot` → `RunTransplantImporter.Import` → `RunDriver.RunOneCombatFromTransplantAsync`。第一个决策可能是开战时的选牌（如工具箱） |
| `{"op":"step","action":i}` | 下一个决策的帧 | 执行候选 i。战斗结束时回结束帧：头部 1 为 12，4 为 1，5 为是否赢下，候选数为 0；之后再 step 报错 |
| `{"op":"save","slot":k}` | UTF-8 `ok` | 把当前战斗状态复制到槽位 k（`CombatState.Clone`）。只在战斗的顶层决策允许，选牌途中、开战时的选牌、结束后都报错。同号槽位覆盖 |
| `{"op":"load","slot":k}` | 当前决策的帧 | 从槽位再克隆一份接着走，槽位本身不动，可反复载入。任何时候都能载入（会丢下当前的局面，包括选牌途中、已结束、出错后） |
| `{"op":"reseed","seed":n}` | 同一个决策的帧 | 确定化，见第四节。`seed` 为 64 位无符号整数 |
| `{"op":"state"}` | UTF-8 JSON | 调试与测试用：候选（下标、动作类型、文字说明、对象 A / B）、回合、能量、玩家与每个敌人的生命 / 格挡 / 能力、手牌（ID、升级、费用）、各牌堆张数、药水；选牌时另有 `select`（发起者、最少 / 最多张数、选项、已选下标） |
| `{"op":"close"}` | 不回帧 | 退出（同 Sts2Headless） |

观测帧现在由临时编码器输出（`TempObsEncoder`）：格式 19 的合法帧，填了头部 0–11 与 13（版本、决策类型、记录数、候选数、结束 / 获胜、幕、层、生命、最大生命、金币、是否战斗中、本会话已执行的决策数），记录有全局、每个生物（按战斗顺序）及其能力、手牌、药水，选牌时还有候选牌（区域 8）与已选的牌（类型 13）。候选整数的 A、B 指向这些记录；特权特征、候选特征全为 0。**这个帧只够联调，不能给模型做决策。** 观测移植（`ObsPort/`）完成后，把 `Server.Encoder` 换成移植版即可，接口是 `IObsEncoder.Encode(Session)`。

## 三、会话与候选

**逐步推进。** sts2-sim 的战斗是异步的，靠决策源驱动。会话自己就是决策源：要战斗决策时返回一个挂起的任务，游戏停在这里，等下一条请求来了再完成这个任务，游戏接着跑到下一个决策点。驱动循环照 `RunDriver.DriveCombatAsync` 的战斗部分写（不自动用药水、不领奖励）。`RunDriver` 只负责进房间、开战斗；它第一次要战斗决策时交给会话自己的循环，并拿到一个永不完成的任务。开局和载入走的是同一条循环，所以原始状态与克隆状态的行为一致。续延一般就地执行；万一 .NET 因为栈太深改到线程池上执行，会话也会等到游戏停下再回应（测试里一次都没有发生）。

**候选的内容与顺序**照 Sts2Headless 的 `RunSession.CombatDecision`，策略网络按下标出手：

1. 手牌逐张（手牌顺序），能打的牌（sts2-sim 的 `CardModel.CanPlay`）× [无目标 + 活着的生物（按战斗顺序：我方在前、敌方在后）]，目标按游戏 v0.111.0 的 `CardModel.IsValidTarget` 判断：无目标只在牌不是 AnyEnemy / AnyAlly 时可以；有目标时 AnyEnemy 对敌方、AnyAlly 对我方，其余都不行。不看能否被攻击（同游戏）。
2. 药水按栏位顺序，可用条件同 Sts2Headless 的 `UsablePotions`（能用药水、玩家没死、通过自定义可用检查、随时可用或战斗中可用），目标按游戏的 `PotionModel.IsValidTarget`：单体类（Self、AnyEnemy、AnyPlayer、AnyAlly）必须有目标，Self 类的目标是玩家自己。
3. 最后是结束回合。

**卡牌效果里的选牌**拆成逐张选 + 确认（同 `CardSelectDecision`）：候选为还没选的选项（按请求里的顺序），已选张数达到下限后加“确认”；选满上限自动提交；没得选（上限为 0，或必须全选）时直接提交，不占一个决策。战斗中的选牌没有“取消”：游戏里只有休息处、奖励等处的选牌可以取消（`CardSelectorPrefs.Cancelable`）。sts2-sim 把“选一张牌”界面的可跳过（发现、无色药水、攻击药水等，游戏的 `FromChooseACardScreen(canSkip)`）写成最少 0 张、可取消，对应 Sts2Headless 的最少 0 张、一开始就有“确认”。牌组里的选牌（`FromDeckFor*` 等走整局选牌源的）也接到会话上，同 Sts2Headless 接管所有选牌界面。

**编码观测要用的东西**都在 `Session` 上：`Run`（导入的整局状态，幕、层、地图从这里取）、`Combat`（当前战斗；载入后是克隆，它的 `RunState` 是战斗用的外壳）、`Player`、`Cands`（每项有动作类型、对象 A、B、文字说明）、`Selecting`（选牌请求、选项、已选下标、最少 / 最多张数）、`Kind`、`Over`、`Won`、`Steps`。

## 四、reseed

语义同 Sts2Headless 的 `RunSession.Reseed`：眼前看得到的局面不变，只换看不到的未来。决策不能读真实随机数（项目硬规定），搜索在 reseed 之后的世界里推演。

- 换的：整局随机数流中与战斗有关的全部（洗牌、战斗生成卡牌 / 药水 / 球、选牌、费用、目标、怪物行动、杂项），玩家的随机数流（奖励、商店、变换），每个敌人自带的随机数；然后用新随机数重洗抽牌堆。
- 不换：开局、问号房、宝箱三条与本场战斗无关的流。
- 做法：就地改随机数对象的内部状态（`Rng.LoadFromSerializable`），引用它们的对象都跟着换；各流的新种子由请求的种子、流的类别与编号经 SplitMix64 派生，同一种子必然得到同一组随机数。
- 已知局限（与 Sts2Headless 相同）：被效果明确放到牌堆顶的牌，玩家其实知道位置，这里也一并打乱了。另外，战斗中新召唤的怪物按整局种子与站位派生自己的随机数，不受 reseed 影响。

## 五、测试结果（2026-11-01，A）

语料：`/root/ext/simcorpus/combats.jsonl`，第 138,251 版模型在真实引擎上贪心打 2 局的 40 场战斗（普通 21、精英 11、Boss 8），1,309 个决策。命令：

```
Sts2SimServe servetest <combats.jsonl> <vocab.txt> [最多几场 [speed]]
python3 serve_smoke.py <Sts2SimServe.dll> <combats.jsonl> <vocab.txt> [第几场]
```

## 六、遗留问题

- **观测**：临时编码器只能联调。选牌决策里 Sts2Headless 会给升级类选牌的候选挂上“升级后的复制品”（对象 B，区域 12），选牌说明还要提示语、发起的选牌命令；sts2-sim 的选牌请求只有发起者（`Request.Source`），没有提示语和命令名，`Cand.B` 现在为空。观测移植时要从发起者推出这两项，或者在 sts2-sim 的 `CardSelectCmd` 上补。
- **目标合法性**：卡牌候选照游戏不看能否被攻击，sts2-sim 自己的 `RunDriver.ValidatePlayCard` 却要求目标在 `HittableEnemies` 里。会话的驱动循环直接调 `engine.PlayCardAsync`，不经过这个校验；如果遇到活着但不能被攻击的敌人，sts2-sim 打出的结果可能与游戏不同。语料里没有遇到。
- **保真度**：候选与局面的剩余差异都来自 SIMC0000 抽到的同名牌副本不同，等方案.md 里的抽牌堆顺序对拍查清。
