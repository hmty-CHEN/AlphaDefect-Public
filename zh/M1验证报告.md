# M1 整局流程验证报告（2026-10-24）

结论：**无头引擎已能完整打完一局 A10。** 整局流程全部走通，包括事件（含多页、事件中开战、小游戏）、战斗奖励与额外奖励、卡牌奖励（挂起式）、卡包、商店、休息处、宝箱、每幕开始的先古事件、第三幕双 Boss，以及终局事件 The Architect。五个角色在无敌模式下各跑 40 局，正常模式下各跑 100 局，均无卡住、无游戏报错，整局结果跨进程确定。

## 一、决策接口

`engine/Sts2Headless/Engine/RunSession.cs`：`GetDecision()` 给出当前决策点和全部合法候选，`Choose` / `ChooseMany` 执行后推进到下一个决策点。

| 决策类型 | 何时出现 | 候选 | 实现方式 |
|---|---|---|---|
| Combat | 战斗中、出牌阶段 | 每张可打的牌 × 合法目标（`CanPlayTargeting`）、每瓶可用药水 × 合法目标、结束回合 | 界面使用的逻辑入口（`TryManualPlay` 等） |
| CardSelect | 任何选牌界面（弃牌、消耗、升级、删牌、变化、附魔、三选一等） | 若干张牌，选 min..max 张 | 游戏的 `ICardSelector` 接口，返回挂起任务 |
| CardReward | 领取卡牌奖励时 | 每张牌、跳过、重抽等替代项 | 假选牌界面，接管 `OptionSelected()`，走正式游戏的异步流程 |
| Bundle | 三选一卡包 | 每个卡包 | 假卡包界面 + 关闭测试分支（测试模式下永远选第一个） |
| Rewards | 战斗结束、事件或遗物给奖励时 | 每个可领奖励、药水栏满时丢弃药水、离开 | 游戏的 `RewardsSet.testSelector` 钩子 |
| Event | 事件进行中 | 未锁定的选项 | `EventSynchronizer.ChooseLocalOption`；“继续”类选项按界面做法直接 `Chosen()` |
| Minigame | Crystal Sphere 事件 | 每个格子 × 小/大工具 | 假界面，直接调用小游戏的 `SetTool` + `CellClicked` |
| RestSite | 休息处 | 可用选项；选过一项后可离开 | `RestSiteSynchronizer.ChooseLocalOption` |
| Shop | 商店 | 买得起的每件商品、删牌、离开 | `MerchantEntry.OnTryPurchaseWrapper` |
| Treasure | 宝箱 | 每个遗物、跳过 | 开箱流程照搬 `NTreasureRoom.OpenChest` 的逻辑部分 |
| Map | 当前房间结束 | 可前往的节点、可在地图上使用的药水 | 可走规则照搬 `NMapScreen.RecalculateTravelability` |
| GameOver | 一局结束 | — | 胜负取自游戏的 `RunManager.OnEnded(isVictory)` |

## 二、为保真做的工作

### 2.1 测试模式里改变内容的分支

游戏的测试模式不只是跳过动画，有几处改变了游戏内容。逐一核对全部 130 个读取 `TestMode` 的方法（清单见 `engine/audit/v0.107.1/testmode-branches.txt`），以下 4 处在执行期间临时关闭测试模式，走正式分支：

| 方法 | 测试模式下的行为 | 正式游戏 |
|---|---|---|
| `Cauldron.GenerateRewards` | 固定 5 瓶药水 | 随机药水 |
| `CallingBell.GenerateRewards` | 固定 3 个遗物 | 按稀有度随机 |
| `MerchantRoom.Exit` | 不写本层历史 | 写入未购买的卡和遗物 |
| `CardSelectCmd.FromChooseABundleScreen` | 永远选第一个卡包 | 玩家选择 |

另外，`FromChooseACardScreen` 的测试分支把最少选择数固定为 0（总能跳过），而正式界面只有 `canSkip` 时才能跳过，已修正。

### 2.2 界面里的游戏逻辑

正式游戏里有些改变状态的步骤写在界面节点中，无头下不会运行。新增 `audit-ui` 命令，扫描界面层调用的全部逻辑层方法（453 项，见 `engine/audit/v0.107.1/ui-to-logic-calls.txt`），逐项复核后复刻了以下流程：

- 战斗胜利后发奖励，或不给奖励时直接继续（`NCombatUi.OnCombatWon`）；
- 奖励界面的“继续”：普通房间继续前进，Boss 房间换幕，双 Boss 时前往第二个 Boss（`NRewardsScreen`）；
- 宝箱的开箱、遗物发放、空宝箱（`NTreasureRoom`、`NTreasureRoomRelicCollection`）；
- 商店删牌后标记已用、禁止删牌时进店即标记（`NMerchantCardRemoval`）；
- 地图可走规则（`NMapScreen`）；
- Crystal Sphere 小游戏（`NCrystalSphereScreen`）。

### 2.3 逻辑层里没有保护的界面访问

游戏逻辑代码在少数地方直接访问界面对象且不判空（开发者的单元测试没有覆盖这些内容）。这类访问一旦抛异常，就会中断同一方法里后面的逻辑，例如 Capacitor 加球位、Amalgamator 合并卡牌、事件里的给金币。处理原则如下：

- **界面单例默认保持为 null**，与开发者的单元测试环境一致，大部分逻辑代码就是按这个前提写的。
- 只有确认会被逻辑执行到的单例才给假对象：`NGame`、`NAudioManager`、`NDebugAudioManager`、`NMapScreen`、`NEventRoom`（及其 `Layout`）。假对象上被逻辑调用的方法全部由 `UiCallStubber` 置空。
- Kaiser Crab Boss（Crusher / Rocket）的背景节点给假对象。
- SoulNexus 的死亡回调里，界面调用是方法最后一句，只吞掉空引用。
- Trial 事件的肖像特效整体跳过。

做过一次反向尝试：把 `NCombatRoom` 也给成假对象。结果原本被 `?.` 跳过的大量界面代码开始执行，引出更多问题，最终撤回。

### 2.4 不能用的补丁方式（经验）

- **不能给 async 状态机的 `MoveNext` 打 Harmony 补丁**：连原样转译都会让 Amalgamator 事件抛空引用。M0 的“帧耗时转译”改成了在被调用方打补丁（假 `SceneTree`、`GetProcessDeltaTime` 返回大值）；`Task.Delay` 改为直接给它打补丁，只在游戏逻辑线程上立即完成。
- **不能指望给自动属性的 getter 打补丁**：它会被 JIT 内联进调用方（`NGame.Instance` 实测如此）。改为直接写后备字段。

### 2.5 已知偏差

- 卡牌奖励打开后又放弃，本次奖励界面不再提供这一项（界面上可以重新打开）。这是为了防止随机策略来回开关形成死循环。只要不开后再放弃，结果就相同。
- Trial 事件的 DoubleDown 选项不提供：它只会弹出“放弃本局”确认框，等于认输。
- 尚未与正式游戏对拍，以上保真工作都基于源码核对和长时间随机测试。

## 三、测试结果

| 测试 | 结果 |
|---|---|
| 无敌模式（每场战斗给 999 覆甲和再生，同官方 AutoSlay），五角色 × 40 局 | 0 卡住，0 游戏报错。胜 9/14/23/13/18 局，其余死于不看格挡的机制（如第二幕 Boss 的沙坑倒计时） |
| 正常 A10 随机策略，五角色 × 100 局 | 0 卡住，平均走到第 4 层左右 |
| 整局确定性 | 五个角色同种子同动作完全一致（无敌模式下 1000–2400 步）；跨进程一致 |
| 一局完整流程 | 约 1200–2400 个决策，用时约 3 秒（随机策略，含无敌模式的长战斗） |

## 四、性能

- 进程启动约 1.5 秒（IL 扫描约 1 秒）。
- **每幕生成地图约 90 毫秒**，是开局的主要开销，一局三幕约 270 毫秒。慢在游戏自己的路径剪枝算法（`MapPathPruning.FindMatchingSegments`，每幕枚举上万条路径）。这是确定性的纯计算，不改。可选的缓解办法：战斗训练直接从战斗开局重置，不需要地图；整局训练用固定种子池，预先生成地图并缓存。
- 其余决策平均约 0.2 毫秒。

## 五、下一步

1. **观测与动作的结构化导出**：目前候选项只有文字标签，需要导出成训练用的结构化特征（实体属性、效果签名、候选编码），以及 Python 接口与多进程。
2. **战斗开局直接构造**：战斗课程（技术路线 5.2 节）需要不经地图、直接按牌组和遭遇开局。这也能绕开地图生成的开销。
3. **与正式游戏对拍**：用游戏自带的战斗回放（`CombatReplayWriter`，含校验和）或记录模组。
4. **状态复制**：评估深拷贝；或在可直接构造战斗开局之后，用“开局 + 动作前缀重放”实现。

## 六、补充：结构化接口与多进程（2026-10-24）

- **观测与候选**：实体记录 + 候选列表的定长数组格式，见 `观测格式.md`。抽牌堆顺序只放在特权特征里，公开观测按 ID 排序。
- **词表与内容目录**：`engine/catalog/vocab.txt`（1873 项，只追加）与 `engine/catalog/v0.107.1/catalog.json`。后者包含静态属性和效果签名（重写的钩子、调用的命令、引用的模型），重复生成时词表新增为 0。
- **战斗开局**：`CombatSpec` 可直接指定角色、进阶、幕、遭遇（具体 ID 或按类别从该幕遭遇池随机抽取）、牌组（含升级）、遗物、药水、血量、金币，不生成地图、不走 Neow。遗物按正式的获得流程加入，会触发获得时效果。
- **Python 接口**：`python/sts2env`，含 `Sts2Env`（单进程）和 `VecEnv`（多进程，同步与异步两种收发）。Python 环境：`.venv`（uv 建立，Python 3.12，numpy）。
- **确定性**：经过管道接口，同一组动作序列在不同进程里得到逐字节相同的观测。
- **修正**：开新局时清掉上一局遗留的挂起状态（奖励界面、假界面等），否则战斗模式开局会收到上一局的奖励决策。

### 性能

| 测量 | 结果 |
|---|---|
| 引擎内每步（战斗，随机策略，含观测编码） | 1.33 ms（优化前 1.63 ms） |
| 其中：执行动作 / 观测编码 / 判断决策点 | 约 1.0 / 0.4 / 0.2 ms（优化前测得） |
| 战斗模式开局 | 约 3 ms（不生成地图） |
| 本机，异步收发，随机策略 | 1 进程约 700–930 决策/秒，4 进程约 3000，14 进程约 3800–4300（16 线程全部占满） |
| 本机，整局模式，14 进程 | 约 2300 决策/秒（含每幕 90 ms 的地图生成） |

性能补丁：游戏的 `CombatState.Creatures / PlayerCreatures / Players` 每次读取都用 LINQ 新建列表，遍历钩子时会被反复调用，剖析显示占战斗模拟一半以上的时间。改为在生物列表不变时返回同一份快照。五个角色的整局结果在有无此补丁时完全一致。

剩余的开销主要是游戏自身的钩子遍历和临时分配，以及观测编码。每个引擎进程实际占用 0.9–1.3 个核（含 GC 与 JIT 后台线程），调整 GC 参数影响不大。后续可以继续优化观测编码（直接写数组，免去 List）。不过收集吞吐最终受 CPU 核数限制，与路线文档第十二节“租机时 CPU 核数决定收集速度”的判断一致。
