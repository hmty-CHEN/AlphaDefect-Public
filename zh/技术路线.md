# 杀戮尖塔2 强化学习技术路线（2026-10-24）

目标：用纯强化学习（不用任何语言模型）训练一个《杀戮尖塔2》原版 AI，在最高进阶（A10）下高胜率通关；游戏更新后只需少量补训练就能恢复水平。

**当前范围（2026-10-24 起）：只训练故障机器人（Defect）。** 引擎和接口保留全部五个角色，以后可能扩展。下文中“五个角色”的部分（5.4 节、各阶段验收）以 Defect 为准；资源估计见 12.5 节。

本文先给结论，再写依据和做法。“已核实”指本机检查过；“待验证”留给 M0 原型确认。

## 一、结论

1. **引擎不重写，直接运行游戏自己的逻辑。** STS2 是 Godot 4 + .NET 9，全部玩法逻辑在托管程序集 `sts2.dll` 里。我们在普通 .NET 进程中加载它，用 Harmony 只拦截表现层（动画等待、特效、音效、界面节点），不碰规则代码。这样每次更新只需替换 DLL、修补少量拦截点，规则永远与正式版一致。这一条是“更新后能快速恢复”的前提，优先级最高。
2. **一个共享编码器，分两层训练。** 战斗和爬塔共用同一个实体编码器（卡牌、遗物、药水、能力、敌人共用表示），按决策类型分输出头。训练上分层：战斗可以从任意战斗开局重置、大量单独练；爬塔决策在整局中练。两层用同一个“整局胜率”价值函数连接：战斗的奖励是战后局面价值减去战前局面价值，而不是手工设计的扣血公式。
3. **动作用“候选打分”，不用固定输出层加掩码。** 每个决策点由引擎列出全部合法候选（某张牌打某个目标、某瓶药水、结束回合、地图节点、奖励项、商品、事件选项等），网络对每个候选编码后打分取 softmax。非法动作根本不出现，新卡、新事件选项也不需要改输出层。
4. **实体用“属性 + 效果签名 + ID”表示，ID 只是补充。** 属性和效果签名都从 `sts2.dll` 自动提取（反射读数值，静态分析代码读它调用了哪些命令和钩子），不需要文本模型。平衡性改动只改数值，模型能直接读到；新内容零样本可用，再小规模微调。
5. **算法沿用上个项目已验证的组合**：PPO + GAE，训练期价值网络可看隐藏信息（抽牌堆顺序、敌人随机数），策略只看公开信息；KL 约束、熵退火、复式评测。后期在战斗上加确定化搜索做策略提升（专家迭代），提高高进阶下的精确度。
6. **杰米尼方案里的 7B 小模型、人类存档模仿学习不采用**；动作掩码、剥离渲染、奖励塑形三条建议采纳，但都换成更适合本项目的形式（第十节）。

## 三、无头引擎

### 3.1 结构

```text
Python 训练端（PyTorch）
   │  批量观测 / 动作（共享内存或本地套接字，二进制定长格式）
   ▼
C# 宿主进程 × N（.NET 9，Linux 原生运行，每进程一局）
   ├─ 加载本机 sts2.dll（只引用安装目录，不复制、不分发）
   ├─ Harmony 补丁：只拦表现层（等待、动画、特效、音效、节点、平台、日志）
   ├─ 决策适配层：把游戏里所有“需要玩家选择”的地方统一成「决策点 + 候选列表」
   ├─ 观测导出：公开观测 + 训练期专用的隐藏信息
   └─ 内容目录：启动时反射扫描 ModelDb，导出全部实体的属性和效果签名
```

驱动方式是直接调用游戏逻辑层（`RunManager`、`CombatManager`、动作队列、`ICardSelector` 等），不点击界面。`AutoSlay` 的各个房间处理器告诉我们每类房间要走哪些步骤，可以照着改写成逻辑层调用。

### 3.2 决策适配层

这是引擎里最需要做全的部分。上个项目曾因“选项框类交互没覆盖、技能在没有选项时自动发动”付出过代价（ddz-engine 决策记录 60），所以：

- 所有选择入口都走同一个接口：打牌（含目标）、用药水（含目标）、结束回合、卡牌选择界面（弃牌、消耗、从牌堆选牌、升级、变化、附魔等）、地图选路、战后奖励、商店、事件选项、休息处、宝箱、Boss 遗物。
- 游戏若在没有接管的地方请求选择，直接报错并记录调用栈，不允许默认选第一个后继续。
- 每局设决策数和动作数上限，防止死循环拖住训练。

### 3.3 正确性：与正式版对拍

用一个很小的“记录模组”装在正式游戏里，记录种子、角色、进阶、每个决策的选择和每层结束时的回放校验和。无头引擎读同一份记录重放，逐层比较校验和。对拍覆盖五个角色、各类房间，每次游戏更新后重新跑一遍。这一步决定我们能不能放心地在无头引擎里训练出来的模型直接上正式版。

### 3.4 状态复制

后期搜索需要“从当前战斗状态分叉”。两种办法，M0 都要试：

1. 深拷贝战斗状态（含随机数状态）；
2. 从战斗开始按动作前缀重放（依赖确定性，实现简单，代价是重放时间）。

即使前期不做搜索，也要在 M0 就确认确定性，因为对拍、复式评测、问题复现都依赖它。

### 3.5 并行与吞吐

`CombatManager` 等是单例，先用多进程（每核一个宿主进程）。之后可以试每个进程开多个 `AssemblyLoadContext`，每个上下文有独立的静态状态，从而一个进程跑多局、合并推理批量。

吞吐目标在 M0 实测后再定。粗算：一局约 15–20 场战斗、每场 30–60 个动作，加上 50–100 个爬塔决策，一局约 1000 个决策。按上个项目的经验，1e9 决策量级可以练出强策略，也就是约 100 万局；战斗单独重置训练会把大部分样本放在战斗上，整局数会少得多。

## 四、表示

### 4.1 实体

每类实体（卡牌、遗物、药水、能力/状态、敌人、意图、附魔、诅咒类、球）的向量由三部分相加：

| 部分 | 来源 | 作用 |
|---|---|---|
| 数值属性 | 反射读取：费用、类型、稀有度、目标类型、关键字（消耗、保留、虚无等）、伤害/格挡/层数等动态数值、是否升级及升级差值 | 平衡性改动直接体现在输入里 |
| 效果签名 | 静态分析该类的代码：重写了哪些钩子（打出后、回合开始、受伤时等），调用了哪些命令（伤害、格挡、施加某能力、抽牌、生成卡牌等）及其参数 | 不靠文本也能知道“这张牌做什么”；新内容零样本可用 |
| ID 嵌入 | 词表只追加不重排；新 ID 初始化为 0 | 学习属性和签名表达不了的细节 |

训练时以一定概率把 ID 嵌入置零（上个项目的“去 ID 蒸馏”），迫使网络主要依靠属性和签名。

### 4.2 局面

- 战斗：自己（体力、格挡、能量、能力、球等）、手牌、抽牌堆/弃牌堆/消耗堆的内容（抽牌堆只给集合，不给顺序）、敌人（体力、格挡、能力、意图及数值）、回合数、本回合已打出的牌。
- 爬塔：角色、进阶、幕与层数、体力、金币、牌组、遗物、药水、地图（节点类型图，用小型图网络或按路径展开）、当前房间信息。
- 编码器：按实体集合做 Transformer（集合内无序），再与全局特征合并。决策类型决定用哪个输出头和价值头。参数量先定在 2M–8M。

### 4.3 动作

候选打分：每个候选由“动作类型 + 涉及实体的向量 + 目标的向量”拼成，与局面向量一起过一个小网络得到分数。打牌带目标时直接枚举“牌 × 目标”（手牌最多 10 张、敌人通常不超过 5 个，候选数很小），不必自回归。卡牌选择界面要选多张时，按“逐张选 + 确认”自回归，整个回答算一个时间步（沿用上个项目“一次回答 = 一步”的做法）。

## 五、训练

### 5.1 分层的含义

| 层 | 决策 | 每局次数 | 训练方式 |
|---|---|---|---|
| 战斗 | 出牌、目标、药水、战斗内选牌 | 约 600–1000 | 从“战斗开局”直接重置；奖励来自整局价值的变化 |
| 爬塔 | 选路、拿牌/跳过、删牌、升级、商店、事件、休息、遗物 | 约 50–100 | 整局 PPO；价值 = 当前局面下的通关概率 |

两层共享编码器，但样本来源和优化器步调可以不同。爬塔层的样本少、方差大，需要单独的批次统计和较小学习率。

### 5.2 战斗课程

战斗开局分布按阶段变化：

1. 初始牌组打第一幕普通怪；
2. 随机模拟“拿过若干次奖励”的牌组，打各幕普通怪、精英、Boss；
3. 换成当前爬塔策略实际打出来的牌组和局面（从整局数据里截取战斗开局），分布与实际一致；2026-10-26 起第 3 步覆盖三幕的普通战、精英战和 Boss，第 1–2 步只留幕末规模的随机构筑（15%），按进度出题停用（决策记录第 80 条）；
4. 全部在 A10 进行。引擎按游戏原样支持所有进阶等级，但训练和评测只用 A10（2026-10-24 确定）；不做进阶课程，冷启动的难度由第 1–2 步的战斗课程来缓解。

这样战斗层在爬塔层还很弱的时候就能看到中后期的强敌，样本效率远高于只靠整局。

### 5.3 爬塔训练

战斗层先练到稳定，再开始整局训练。整局训练时战斗层继续更新，但用 KL 约束防止被爬塔层的低质量局面带偏。牌组相关决策（拿牌、删牌、商店）后期可以加“前瞻”：对候选牌组，用战斗价值头估计接下来几场典型战斗的表现，作为额外特征或搜索依据。

### 5.4 角色

五个角色用同一个模型，角色作为输入；共享的无色牌、遗物、药水、敌人知识可以互相迁移。若某个角色明显落后（Epoch 的数据里 Necrobinder 对各家都更难），再从共享模型分出该角色做微调，最后蒸馏回来。

### 5.5 算法细节（沿用并调整上个项目）

- PPO + GAE；战斗内 γ 取 1 或接近 1，爬塔层 γ = 1。
- 价值网络额外看隐藏信息（抽牌堆顺序、敌人随机数状态、未来地图事件），策略只看公开观测。
- 熵系数退火；必要时加 MMD 式“磁铁”KL 到慢速参考策略。
- 不需要行为克隆冷启动：单人游戏、动作已枚举合法，随机策略在第一幕普通战斗里也能拿到有效信号。若冷启动太慢，再用 `AutoSlay` 或简单规则脚本做少量行为克隆。

## 六、奖励

| 层 | 奖励 | 说明 |
|---|---|---|
| 整局 | 通关 +1，失败 0 | 最终目标。可加按幕的势函数塑形（到达第 N 幕的经验通关率），势函数塑形不改变最优策略 |
| 战斗（前期） | 战后 −k × 损失体力 − 消耗药水的估价；战败 −1 | 冷启动用的近似 |
| 战斗（后期） | V(战后局面) − V(战前局面)，V 为爬塔层的通关概率 | 自动权衡“多掉血换更快结束”“留药水到 Boss”等问题 |

不建议用“造成伤害”作为奖励：打掉敌人体力本身不是目的，它会诱导网络在不该进攻时进攻（比如敌人有反伤或要先叠格挡的回合）。如果需要更密集的信号，用势函数形式的“敌人剩余体力比例”，在战斗结束时自然抵消。

## 七、搜索（第二阶段）

模型无关的 PPO 能学到不错的战斗直觉，但最高进阶需要精确计算（斩杀线、格挡是否够、出牌顺序）。第二阶段在战斗上做确定化搜索：采样若干个“抽牌顺序与敌人随机数”的可能实现，用策略网络作先验、价值网络作叶子估值，做 Gumbel 式的有限候选搜索。搜索结果一方面直接用于对局，另一方面作为策略训练目标（专家迭代），把搜索能力蒸馏回网络。这仍是纯强化学习（AlphaZero 一类），只依赖我们自己的模拟器。

能否做取决于 3.4 节的状态复制速度，M0 先测。

## 八、版本更新适配

这是本项目的硬要求，从第一天按以下方式设计：

1. **引擎层**
   - 规则全部来自 `sts2.dll`，不手写；补丁只放在表现层和决策入口，按“函数签名 + 版本”登记，更新后启动时自检，哪个补丁目标找不到就直接报出来。
   - 每次更新跑冒烟测试：五个角色、随机策略和 `AutoSlay` 各跑若干局，统计异常、卡死、未接管的选择入口。
   - 重新跑 3.3 节的对拍。
2. **内容层**
   - 每次启动导出内容目录（全部实体的属性和效果签名），与上一版本做差异：新增、删除、数值改动、效果签名改动。
   - 词表只追加；删除的 ID 保留空位。
3. **模型层**
   - 检查点按“手术”规则扩展：新输入对应权重补 0，保证扩展后对旧内容的输出不变（上个项目 9.2 节的做法）。
   - 补训练：从最新检查点继续，让改动过的内容以较高比例出现（含这些卡/遗物/敌人的战斗和局面），其余照常防止遗忘；KL 约束拉向更新前的策略，系数逐渐衰减。
   - 只改数值的平衡补丁，通常零样本就能大部分保持水平，补训练以小时计；大型内容更新（新角色、新幕）需要更长的补训练。
   - 连续补训练会让模型停在较低水平（OpenAI Five 的经验），所以每隔几个大版本用当时的完整内容从头重训一次，可用旧模型蒸馏热启动。
4. **零样本能力的度量**：训练时固定留出约 10% 的卡牌、遗物和事件（按名字哈希），只在评测时出现。“留出内容上的胜率”直接反映下一次更新时的接入成本。

## 九、评测

- **复式评测**：固定一组种子（同角色、同进阶、同地图与随机数），新旧模型各打一遍，用配对差值比较，抵消运气。
- **指标**：各角色 A10 通关率（主指标）、平均到达层数、各幕 Boss 战胜率、战斗平均掉血；留出内容上的同样指标。
- **对照**：随机策略、`AutoSlay`、历史检查点。
- **正式版抽查**：定期用记录模组让模型在正式游戏里打若干局，确认无头引擎训练的结果在正式版上成立。

## 十、对杰米尼方案的取舍

| 杰米尼的建议 | 取舍 | 理由 |
|---|---|---|
| 宏观层用 7B–8B 小语言模型 | 不采用 | 本项目不做语言模型；爬塔决策的“语义”可由属性和效果签名提供 |
| 用人类高手存档做模仿学习 | 不采用 | 拿不到成规模、含战斗过程的高手数据；单人游戏有模拟器，自生数据足够 |
| 宏观、微观拆成两个独立网络 | 部分采用 | 训练分层，但共享编码器：两层看的是同一批卡牌、遗物，分开学是重复劳动，也更难同步适配更新 |

| 用 Hook/Mod 剥离渲染和动画计时 | 采用并更进一步 | 不启动 Godot，直接在 .NET 中运行 `sts2.dll` |
| 前期用 ΔPlayerHP − α·ΔEnemyHP 做密集奖励 | 改写 | 去掉“造成伤害”奖励；前期用体力与药水损失，后期换成整局价值差（第六节） |
| 未涉及 | 补充 | 隐藏信息只给价值网络、确定性与对拍、版本更新流程、复式评测、后期搜索 |

## 十二、参数量与算力

### 12.1 参数量

起步用 1M–4M 参数，逐步扩到 10M–30M；不在一开始就上几千万。

- **局面不大。** 手牌最多 10 张，敌人通常不超过 5 个，牌堆、遗物、能力可以按类汇总成少数几个记号。每次决策约 30 个记号，远小于上个项目的事件历史。
- **难点不在容量。** 战斗的难点是精确计算（斩杀线、格挡够不够、出牌顺序），神经网络靠加参数学精确算术效率很低，搜索（第七节）更有效。爬塔的难点是长期规划和稀疏奖励，靠的是样本量和价值估计的质量。
- **推理成本决定上限。** 一局约 1000 次决策，每次都要过一遍网络。按实体 Transformer、每次约 30 个记号粗算，前向计算量与参数量成正比：

  | 规模 | 宽度 × 层数 | 参数 | 每次决策前向 |
  |---|---|---|---|
  | S | 128 × 3 | 约 0.9M | 约 0.05 GFLOP |
  | M | 256 × 4 | 约 3.4M | 约 0.2 GFLOP |
  | L | 384 × 6 | 约 11M | 约 0.65 GFLOP |
  | XL | 512 × 8 | 约 25M | 约 1.5 GFLOP |

- **怎么加大。** 沿用上个项目的做法：网络宽度按“保函数加宽”设计，从 S 起步，到平台期时在同样样本量下做 S/M/L 的扩容对比，确实有收益才加大，加宽后的输出与加宽前完全相同，不用重练。
- **降低推理成本的设计**：每种实体的“属性 + 效果签名”编码只与实体类型有关，可以每个版本预先算好查表；抽牌堆、弃牌堆、遗物等按集合汇总，不逐张进注意力；多个对局的决策合批推理。

### 12.2 本机能做到哪一步

本机：i5-12600KF（16 线程），WSL 可用约 47 GB 内存（Windows 共 64 GB），RX 6600 8 GB 在 WSL 下不能用于训练。

上个项目在本机的实测可以作参照：约 56 万参数的网络，约 30 小时完成 1.2 亿个决策的收集和学习，也就是每天 1 亿决策左右。

与上个项目不同的是，STS2 的模拟可能比较便宜（StS2Sim 单线程每秒约 1000 次短模拟），瓶颈很可能是网络推理和学习，而不是规则引擎。这一点 M0 实测后确认。如果确实如此，显卡的作用会比上个项目大得多。

| 阶段 | 大致样本量 | 本机是否够用 |
|---|---|---|
| M0–M1 引擎开发、对拍、冒烟测试 | 不训练 | 够 |
| M2 战斗强化学习（S 规模，一两个角色） | 1e8 量级决策 | 够，约数天 |
| M3 整局、五个角色、A10 | 1e9–5e9 量级决策 | 不够：CPU 上 M 规模 1e9 决策需要以月计 |
| M4 搜索与专家迭代 | 每个决策多几十倍的计算 | 不够 |
| 版本更新后的补训练 | 1e7–1e8 量级决策 | S 规模勉强可以；M 规模以上要显卡 |

### 12.3 租机建议

- **现在不租。** M0–M2 在本机完成，同时拿到三个实测值：每个动作的模拟耗时、每次决策的推理耗时、战斗训练的收敛样本量。
- **M2 结束、准备做整局 A10 时再租。** 配置以显卡为主：一块 RTX 3090/4090，加 32 核左右的 CPU、64 GB 以上内存。若 M0 测出模拟很贵，再加核数。上个项目租用过的“RTX 3090 24G + 36 线程 + 64 GB”这一档就合适。
- **费用量级**：按 M 规模、一块 4090 有效约 20 TFLOPS 粗算，1e9 决策的学习约 1–2 天，收集与学习并行后，五个角色到 A10 的一轮正式训练大约是“一台单卡机器一到两周”。这是数量级估计，M2 之后按实测重算。
- **补训练放哪里**：如果希望每次游戏更新在本机就能补训练，有两个办法：模型控制在 S 规模；或让 RX 6600 可用（Windows 上用 ONNX Runtime + DirectML 只做推理，或装原生 Linux 用非官方 ROCm 支持）。两者都要先测，不作为主路线。

### 12.4 按实测重算（2026-10-24）

12.1–12.3 节是引擎做出来之前的估算，这里用实测数据重算，取代前面的数字。

**实测值（本机 i5-12600KF，16 线程）：**

| 项目 | 实测 |
|---|---|
| 引擎每个决策（模拟 + 观测编码） | 约 1.3 ms 单核 |
| 引擎吞吐，随机策略，14 进程 | 约 4000 决策/秒（16 线程全部占满） |
| 战斗模式开局 / 整局每幕地图生成 | 约 3 ms / 约 90 ms |
| S 网络（0.9M 参数）CPU 推理 / 训练（8 线程） | 约 3800 决策/秒 / 约 1200 样本/秒 |
| M 网络（3.9M 参数）CPU 推理 / 训练（8 线程） | 约 1100 决策/秒 / 约 350 样本/秒 |

结论：在 CPU 上，**网络推理和训练比游戏模拟更贵**；S 网络每个决策的推理就要约 2 ms 线程时间。

**假设：** 能打完 A10 的策略，一局约 1000 个决策（随机策略在无敌模式下为 1100–1800）；PPO 每批数据训练 3 遍；GPU 吞吐按小网络的经验值估算（RTX 4090：M 网络推理约 10 万决策/秒，训练约 3–6 万样本/秒），尚未实测。以下都是数量级估计。

**各方案的速度：**

| 方案 | 收集 | 学习 | 每天可处理的决策 |
|---|---|---|---|
| 本机，S 网络，全在 CPU | 与推理、训练争 16 线程 | 约 400 决策/秒（3 遍） | 约 3–4 千万 |
| 本机，M 网络 | — | 约 120 决策/秒 | 约 1 千万，不实用 |
| 之前租过的机器（RTX 3090 + 36 线程老款至强） | 约 8 千决策/秒 | 显卡，不是瓶颈 | 约 7 亿 |
| 推荐：RTX 4090 + 64 vCPU | 约 1.5–2.5 万决策/秒 | M 网络约 1–2 万决策/秒 | 约 13–17 亿 |
| 两块显卡 + 128 vCPU | 约 3–5 万决策/秒 | 约 2–4 万决策/秒 | 约 30 亿 |

**各阶段的需求：**

| 阶段 | 样本量（估计） | 本机 | 推荐租机（4090 + 64 vCPU，约 1–1.6 美元/小时） |
|---|---|---|---|
| M2 战斗训练试点（S 网络，先一两个角色） | 3 千万–1 亿 | 1–3 天 | 2–6 小时 |

| M4 战斗搜索与专家迭代 | 1 千万个搜索决策 | 不现实 | 每个搜索决策约 32 次模拟，按“重放前缀”恢复状态约 1.3 s CPU，共约 100 小时（做出状态深拷贝后约 40 小时），100–200 美元 |
| 平衡补丁后的补训练 | 2–5 千万 | S 网络 1–2 天 | 0.5–1 小时 |
| 新角色、新幕后的补训练 | 2–5 亿 | 不现实 | 4–9 小时 |
| 定期从头重训 | 同 M3 | — | 2–4 天，100–200 美元 |

**判断：**

1. **本机适合做 M2 试点。** 用 S 网络、单个角色、战斗模式，1–3 天能看出学习曲线，从而量出“达到某个战斗水平需要多少样本”。这是后面所有估计里最大的不确定项。
2. **M3 起必须租机，配置以“显卡 + 多核”平衡为准。** 收集吞吐由 CPU 核数决定，学习吞吐由显卡决定，两者应在同一量级。之前那台 3090 + 36 线程的机器收集偏慢，约是推荐配置的一半。
3. **整个项目的租机费用量级为 500–1500 美元，日历时间 1–2 个月。** 主要不确定项是样本效率，可能偏差 3 倍左右。
4. **能降低成本的工程优化：**
   - 观测编码直接写数组（约 0.4 ms → 0.1 ms）；
   - 一个进程跑多个对局（`AssemblyLoadContext` 隔离单例）；
   - 整局训练用固定种子池并缓存地图；
   - 战斗状态深拷贝（直接决定 M4 的成本）。

   前三项合计可望把收集成本降到约一半。

## 十三、风险与待验证

- **`sts2.dll` 能否在 Linux 的 .NET 9 下运行**：它引用 `GodotSharp.dll`，后者会调用 Godot 原生库。凡是被调用到的 Godot API 都要拦截；若数量太多，退路是在 Windows 上运行宿主进程，或用 Godot 的 `--headless` 模式加模组运行（慢，但完全保真）。
- **异步与等待**：游戏逻辑大量使用 `async`（例如 `AutoSlayer.RunAsync`）。需要一个同步推进的调度器，确保每一步都在等待玩家选择时停下，而不是靠计时器。
- **单例与静态状态**：决定每进程能跑几局，影响吞吐。
- **确定性**：若存在依赖时间或哈希顺序的随机，对拍和搜索都会受影响，需要找到并固定。
- **法律与分发**：只在本机读取已购游戏的 DLL，不提交、不分发游戏文件和反编译代码。

## 十四、待实施：从中途局面开整局（2026-10-26 记下，暂不实施）

背景：评测用贪心、训练按概率采样，训练里打过第二幕 Boss 的局只有评测的一半（15% 对 30%），整局约一半的时间花在已过关九成的第一幕。方案：正常整局换幕时（`RunManager.EnterAct(下一幕)`）导出“开幕快照”——玩家快照、之前每幕走过的层数、已遇到的事件、开局最大生命；之后新开一局（新种子），还原玩家、按层数补地图历史（总层数按历史节点数算）、补已遇事件、把已有遗物从遗物袋移除，再调用同一个 `EnterAct(N)` 接着打完整局（游戏自带的跳幕调试命令也走这条路）。随机数和卡牌稀有度保底计数从头开始。训练侧每个采集进程留“第二幕开局”“第三幕开局”两个池（各 200 份），整局按比例从第一层（50%）、第二幕（35%）、第三幕（15%）开始，配置默认 0；奖励不变；训练的平均层数、前 10%、通关率、死因、Boss 过关率只统计从第一层开始的局，中途开局另记；评测不变。上线前核对还原一致性（同种子打到换幕存快照，再从快照开局逐项比对牌组、遗物、药水、金币、血量、层数、事件、遗物袋）并随机跑通。风险：第一幕整局变少（看评测的第一幕 Boss 过关率）、整局级状态还原不全（比例设回 0 即退回）。工作量约引擎 150 行、训练侧 100 行。
