# AlphaZero 式搜索方案（Rust 引擎 M4 的准备）

2026-10-27 起草。目的：Rust 引擎能复制战斗状态以后，Boss 战的搜索从“价值叶子 + 贪心推演”（`tools/mcts_eval.py`）换成 AlphaZero 式的蒙特卡洛树搜索：每次模拟只走到一个新节点、调一次网络（策略头给先验、价值头给估值），不再贪心走 12 步。本文定算法、对 Rust 引擎的接口要求、Python 端的分工和验证办法。按决策记录第 139 条，搜索排在训练换引擎（M3）之后；本文只做准备，不改变 Rust 会话的优先级。

## 一、为什么现在的做法到头了

- 现在每次推演都让 C# 真游戏引擎从这场战斗开头按已走的动作重放，再 `reseed` 换隐藏随机数、走候选、贪心走 12 步、用价值头估分。一场 Boss 战约 20 个决策要搜，每个约 64 次推演；A 上 16 个进程每 30 分钟只做完约 24 场。
- 推演里的贪心策略本身就是要改进的那个策略，12 步之后的价值估计也只看一个点；推演次数多不上去，只能在“前几名候选里挑一个”。
- Rust 引擎可以直接复制状态（不重放）、每步约 2 微秒，引擎不再是瓶颈；瓶颈变成网络推理。AlphaZero 式的搜索每次模拟只调一次网络，同样的网络调用量能换来深得多的树。

## 二、算法：单观察者信息集蒙特卡洛树搜索（SO-ISMCTS）＋ PUCT

战斗里玩家看不到的随机性：抽牌堆顺序、怪物以后的出招、战斗中随机生成的牌与药水、随机目标等。处理办法沿用现在的确定化（`reseed`：只换玩家看不到的随机数、重洗抽牌堆，玩家看得到的局面不变），但不在每个确定化世界里各建一棵树（那样会“策略融合”：在某个世界里树会利用它知道的下一张牌），而是一棵树建在信息集上：

1. **每次模拟**：从根局面复制一份状态，用这次模拟自己的种子 `reseed`，得到一个确定化世界；沿树往下走。
2. **选择**：在当前节点，只考虑这个世界里实际合法的动作；用 PUCT 选：`Q(a) + c · P(a) · sqrt(N_avail(a)) / (1 + N(a))`，其中 `P(a)` 是策略头在当前观测上的概率（只在这个世界合法的动作上重新归一化），`N_avail(a)` 是该动作“可选”过的次数（信息集搜索的可用性计数，代替父节点访问数）。`Q` 按树里出现过的最小、最大值归一化到 [0, 1]（MuZero 的做法，奖励尺度不必调 c）。
3. **动作的身份**：子节点按“动作键”而不是候选下标区分。不同世界里手牌不同，下标 3 在两个世界里可能是两张不同的牌；动作键 =（动作类型，牌的身份：词表 ID + 是否升级 + 本回合费用，目标的身份：第几个敌人或自己），两张一模一样的打击合成一个动作（顺带减少分支）。
4. **扩展与估值**：走到树里没有的动作就扩展一个子节点，对这个新局面调一次网络，拿策略先验和价值；战斗结束直接用终局得分。不推演。
5. **回传**：沿路径把估值加回去。整场战斗只有一个行动方（玩家），怪物的行动和随机事件都算在“走一步”里，不需要对手的极小化。
6. **决策**：根节点访问次数最多的动作；训练标签用访问次数的分布（温度 1），与 AlphaZero 一致。

**估值的尺度**（与考卷搜索一致）：用战斗课程模式（MODE_COMBAT）的价值头，尺度是战斗回报（赢 1 + Boss 奖励 0.5，输 −1 + 0.5 × 打掉的敌人生命比例，再加血量变化 / 最大生命）；终局按同一公式算（`tools/mcts_eval.py` 的 `score_value`）。价值头能看到特权输入（抽牌堆顶部的真实顺序）——在确定化世界里它看到的是这个世界的顺序，对多个世界平均就是期望，与现在的价值叶子搜索相同，不算偷看真实对局。

**批量推理**：经典 MCTS 每次模拟要等上一次的估值。用“虚拟损失”让一棵树一次挑出 8–32 个不同的叶子一起估值，同时让几百棵树（几百场战斗或几百个决策）并行，凑成上千的推理批交给显卡。

**规模估计**（未实测）：每个决策 200–800 次模拟，每次一次网络前向；一场 Boss 战约 60 个决策，约 1–5 万次前向。按 3090 上推理批量下每秒几万次前向估，一场 Boss 战约 1–2 秒，是现在价值叶子搜索的几十倍以上，树也深得多。

## 三、对 Rust 引擎的接口要求（M4 用，不影响 M1–M3）

优先 PyO3 直接调用（搜索每秒要几十万次复制、走步、编码，进程间通信扛不住）；同一协议的替身进程只用于对拍。

| 能力 | 要求 |
|---|---|
| 复制状态 | `clone()` 得到独立的战斗状态（含全部随机数流的状态），开销在微秒量级；原状态不受影响 |
| 确定化 | `reseed(seed)`：与 C# `RunSession.Reseed` 同样的语义——换掉以后要用的随机数流（跳过 UpFront、UnknownMapPoint、TreasureRoomRelics）、重洗抽牌堆；玩家看得到的局面不变。为了能对拍，算法照搬 |
| 走一步 | `step(action)`，与现在的候选下标语义相同 |
| 动作键 | 每个候选给出稳定的动作键（见上文第 3 点），跨确定化世界不变；Python 端也能从观测算出同样的键作后备 |
| 编码观测 | 观测格式版本 10，与 C# 逐字节一致（含 tok_priv）；支持一次编码一批状态，直接返回拼接好的 numpy 数组（`Ragged` 布局） |
| 终局信息 | 胜负、血量、最大生命、敌人剩余与最大生命合计（输局部分分用） |
| 起点 | 从玩家快照 + 遭遇 + 种子开一场战斗（考卷题目、训练里的真实快照），与 C# `CombatSetup` 一致 |
| 确定性 | 同一起点、同一种子、同一动作序列，结果完全相同（复现与对拍的前提） |

## 四、Python 端的分工

- `python/sts2rl/azmcts.py`（待写）：树、PUCT、可用性计数、动作键、虚拟损失、批量估值调度；后端抽象成“复制 / 确定化 / 走一步 / 编码 / 终局信息”五个操作。
- 后端一：C# 引擎 + 重放（状态 = 开局请求 + 动作序列 + 确定化种子，复制只是复制这个元组，用的时候重放）。很慢，只用来在少量考卷题上核对算法的正确性，不必等 Rust。
- 后端二：Rust（PyO3），M4 时接上。
- 推理服务：沿用学习端的网络与组批（`collate_ragged`），评测时用 bf16 推理；可用学习端提速里的打包注意力（决策记录 144）。

## 五、验证

1. **算法正确性**（C# 重放后端，几十道考卷题、少量模拟）：模拟数为 1 时应等于贪心；模拟数增加时胜率不降；动作键在不同世界之间合并正确（同名同费牌合并、目标区分）。
2. **考卷配对比较**（512 道第二、三幕 Boss 题，同一种子）：贪心、价值叶子搜索（已有：第二幕 +6.2、第三幕 +3.5 个百分点）、AlphaZero 式搜索（模拟数 64 / 256 / 1,024），看胜率与耗时。真实对局在 Rust 上打时，把选出的动作序列在 C# 上重放一遍核对结果（对拍不一致的题单独标出）。
3. **进阶 10 整局**：Boss 战开搜索、其余贪心，与纯贪心同种子配对（第 136 条原本要做的实测）。
4. **蒸馏**：搜索的访问分布作为策略目标、搜索的根价值作为价值目标，回到训练（专家迭代），先在 A 上分叉对照。

## 六、风险

- **动作键定义不当**：合并了不该合并的动作（如费用被改过的同名牌）会让树里的统计混在一起；要在核对阶段专门测。
- **价值头的偏差**：AlphaZero 式搜索比贪心推演更依赖价值头；第三幕第二个 Boss 这类价值头没练好的局面，搜索收益可能有限。必要时叶子改为“价值头 + 短推演”的混合。
- **一致率**：搜索在 Rust 上推演、真实对局在 C# 上打时，个别规则差异只会让推演略有偏差，不会弄错真实结果；Rust 替换训练引擎后，对拍仍是准绳。
