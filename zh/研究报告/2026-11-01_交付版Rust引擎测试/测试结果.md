# 交付版 Rust 引擎测试：速度、对拍与搜索胜率

日期：2026-11-01。被测对象：`.worktrees/main/deliver/sts2-rust-engine-199ca1e`（提交 199ca1e，观测格式 19，自称“对拍率不高，但能支撑 PIMC 搜索”）。被测模型：第 135,634 版（滑动平均权重，千种子复测 73.1% ± 2.8%）。测试在 A 上进行，常规评测暂停两段（11:46–12:02、12:10–12:50，本机时间），复测避开，采集照跑，没有占用 B。用户在全量跑到 493/556 题时要求停止，A 已让出。

## 结论

1. **快：引擎本身比 C# 快 30–50 倍，复制一个状态约 75 微秒。** 走一步（含编码一帧、进程间往返）Rust 0.17–0.19 毫秒，C# 5.8–6.3 毫秒；整场约 125 步的贪心轨迹一次重放，Rust 5.2 毫秒，C# 257 毫秒；8 个进程随机打整场，每秒 27,756 步对 779 步。用到搜索里以后，瓶颈已经不在引擎，而在 Python 与网络前向：A 一台机器 38 分钟做了 142 万次推演（每秒约 610 次），上次 C# 后端两台机器每秒约 186 次。
2. **不准：在真实牌组的第三幕 Boss 上，Rust 与 C# 几乎从第一步就不一致。** 交付说明里的 94.91% 是随机牌组、而且只在两边规则状态一致的步上比帧；换成复测快照题，493 题里 446 题第一个决策的帧就对不上，全部决策里逐项一致的只有 2.1%（不比 5 项 Rust 不填的头部字段时）。按动作重放时，38.5% 的决策 Rust 重放到中途动作下标越界、给不出局面；按帧导入时，导入后不知道这是双 Boss 连打的第几场，记录数、候选数也常对不上。
3. **搜索没有带来显著提升。** 搜索在 Rust 上推演、选出的动作交给 C# 执行，与贪心逐题配对：

   | 接法 | 两场都赢 | 对贪心 | 只有搜索赢 / 只有贪心赢 | p |
   |---|---|---|---|---|
   | 贪心 | 395/493（80.1%） | — | — | — |
   | Rust 重放搜索 | 402/493（81.5%） | +1.4 ± 1.1 个百分点，95% 区间 −0.6 至 +3.5 | 17 / 10 | 0.25 |
   | Rust 导入搜索 | 400/493（81.1%） | +1.0 ± 1.3 个百分点，95% 区间 −1.5 至 +3.5 | 22 / 17 | 0.52 |

   两者方向都为正，但都不显著。作为参照，10-31 的同一算法在 C# 上推演（第 122,056 版）是 +6.7 ± 1.7。这次没有跑同题同模型的 C# 推演对照（用户叫停），所以分不清“Rust 不准吃掉了收益”与“现模型上这种搜索本来就涨得少”各占多少；从机制看前者至少占一部分：重放接法每题只真正搜了 35 次，另有 55 次因为根局面不可用退回贪心。
4. **现在不能用到直播。** 直播只能走导入接法（没有种子，不能重放），而导入接法在 C# 帧上的保真度是本报告里最差的一项，离线也没有显著收益；单步搜索延迟也没能单独测（见第四节）。要等 Rust 引擎修到真实 Boss 局面基本对得上，再用同一套工具重测，并补 C# 推演对照。

## 一、怎么测的

- **题**：第 135,634 版千种子复测里打到第三幕第一个 Boss、记下了开打前快照的全部 556 局（`tools/search_test.py exam`，随机顺序编号），从快照连打两个 Boss。做完的 493 题是随机顺序的前一段。
- **三个臂，同题同种子**：
  - 贪心：每步取网络概率最高的候选，C# 引擎；
  - 重放搜索：真实对局在 C# 上；每个要搜的决策，Rust 从战斗开头按已走的动作重放、reseed、走候选，再贪心推演；
  - 导入搜索：真实对局在 C# 上；每个决策把 C# 当前的帧经交付版配套的翻译层（`.worktrees/main/python/sts2rl/live_import.py`）导入 Rust，复制出各个世界、各自 reseed 后推演。这是直播唯一可用的接法。
- **搜索算法**与 10-31 的搜索测试完全相同：最大概率不到 0.9 时取前 4 个候选（各至少 2%），共同随机数，逐轮减半 2 轮、首轮每候选 4 个世界，推演 12 步后用战斗价值头估值，与贪心项逐世界配对、平均差超过 2 个标准误才改选。不读真实种子，价值头不带特权输入。
- **退回贪心的两种情况**：Rust 给不出根局面（报错）；Rust 根局面的候选与 C# 不同（数量或内容不同，C# 的候选下标在 Rust 里不是同一个动作）。推演中报错的世界不参与比较。
- **根局面核对**：每个决策把 Rust 的根局面帧与 C# 的帧逐项比较（头部、记录、候选；不比特权特征和两个进程级头部项）。“宽松口径”另外不比金币（头部 10）、第二个 Boss（17）、还要打的 Boss 数（25）、商店删牌次数与价格（28、29）——交付版在战斗模式下不填这几项。导入接法另外去掉出怪池记录再比（导入的状态一律按整局模式编码，会多出 17 条）。

## 二、速度

A 上测，测试时采集在跑（负载约 30，36 核），绝对值偏慢，两边条件相同。“本机”是空闲时的 Rust 数，供参考。单位为中位数。

| 操作 | C#（A） | Rust（A） | 倍数 | Rust（本机） |
|---|---|---|---|---|
| 开局（第三幕 Boss 快照，返回一帧） | 9.7 ms | 3.6 ms | 2.7× | 0.70 ms |
| 走一步，随机打法（含编码一帧与往返） | 5.8 ms | 0.17 ms | 34× | 0.08 ms |
| 走一步，贪心轨迹 | 6.3 ms | 0.19 ms | 33× | 0.08 ms |
| 进程内走一步（不编码、无往返） | 约 1.8 ms¹ | 12 µs | — | 3.1 µs |
| 还原：开局 + 重放到第 25 / 50 / 100 步 | 47 / 98 / 191 ms | 3.7 / 3.8 / 4.8 ms | 13–40× | 0.73 / 0.81 / 1.0 ms |
| 开局 + 重放一半 + reseed + 走一步（搜索的一次推演起点） | 30.8 ms | 3.4 ms | 9× | 0.73 ms |
| 复制一个状态（搜索协议，含往返） | 无此操作 | 75 µs | — | 41 µs |
| reseed（含往返） | — | 24 µs | — | 33 µs |
| 复制 + reseed + 走一步，32 个世界平均每个 | — | 263 µs | — | 125 µs |
| 整场贪心推演（约 123–127 步，逐步返回帧） | 907 ms | 30 ms | 30× | 15 ms |
| 整场一次重放（不编码中间帧） | 257 ms | 5.2 ms | 49× | 1.1 ms |
| 吞吐，随机打整场，1 个进程 | 90 步/秒 | 3,405 步/秒 | 38× | 7,521 步/秒 |
| 吞吐，8 个进程 | 779 步/秒 | 27,756 步/秒 | 36× | — |

¹ 由“重放到第 100 步 191 ms、开局 9.7 ms”推算，C# 没有不编码的单步计时。

Python 解析一帧约 25–33 µs。Rust 的单次往返里，进程间通信占了大头（本机进程内 3 µs，往返 80 µs）；要把这部分省掉需要批量协议或 PyO3。

**放进搜索以后**：这次 A 一台机器 38 分钟做完 493 题 × 三个臂，推演 142 万次，每秒约 610 次；10-31 的 C# 后端是两台机器 95 分钟 475 题、106 万次，每秒约 186 次。按机器算快约 6 倍，瓶颈已转到 Python 调度与网络前向（每次推演要 13 次前向，平均每批 36–52 个观测）。

## 三、对拍

### 交付说明里的数字指什么

`frame_diff.py`：随机牌组、各幕遭遇混合 200 场，按 C# 随机打法走，**只在两边规则状态一致的步上**逐字节比帧；starter 牌组 158 帧 100%，random 3,479 帧 94.91%。规则状态一旦分歧，这一场就停止，不计入帧的一致率。所以 94.91% 不是“局面一致的比例”，而是“规则还没分歧时，编码一致的比例”。真实牌组的第二、三幕 Boss 战从没专门测过（交接说明第六节已列为风险）。

### 真实第三幕 Boss 上的实际情况

| | 重放接法 | 导入接法 |
|---|---|---|
| 核对的决策 | 63,759 | 62,558 |
| 逐项一致（严格） | 0（0.0%） | 1,329（2.1%） |
| 逐项一致（宽松口径） | 1,353（2.1%） | 1,329（2.1%） |
| 第一个决策就不一致的题 | 446/493 | 443/493 |
| Rust 给不出根局面（报错） | 24,547（38.5%） | 0 |
| 要搜的步里退回贪心 | 27,322 次（每题 55） | 11,953 次（每题 24） |
| 真正搜索的步 | 17,475 次（每题 35） | 32,613 次（每题 66） |

**重放接法分歧的来源**（第一帧逐题对照 8 题，加上全量的第一处差异统计）：

- 只影响网络输入、不影响规则：第二个 Boss（头部 17）与还要打的 Boss 数（25）没填，网络会以为这是最后一场；商店删牌次数与价格（28、29）、金币（10）、层数（7）没从快照带过来。
- 影响规则：快照里卡牌上的 TINKER 修正（疯狂科学）与 CARDMOD:REPLAY 没导入；有的题开局抽牌数就不同（头部 3、31、33）；有一题 Rust 多了两张 DAZED 和费用修正记录。规则一旦分歧，按 C# 的动作下标重放就会走错，最后下标越界报错（“共 4 个候选，收到 4”这类）。
- 宽松口径下最常见的第一处差异：记录数（头部 2）、层数、能力记录、遗物记录、头部 26（出牌途中能否抽牌）、充能球与卡牌特征。

**导入接法**（C# 帧 → 翻译层 → Rust）：

- 导入的状态一律按整局模式编码，带 17 条出怪池记录，而战斗模式的 C# 帧没有（直播帧是整局模式，本身就有，这一项在直播里不是问题）。
- 头部 23（双 Boss 连打的第几场）丢失，导入后的状态不知道还有第二个 Boss，第一个 Boss 打赢就当整场结束。在不一致的决策里，第一处差异是它的占 33%，最多。
- 开局的选牌（如赌博筹码）丢失：决策类型从“选牌”变成“出牌”，候选数也变了。
- 能力层数等字段被重置（如 WITHERING_PRESENCE_POWER 的显示数）。
- 本机拿 Rust 自己的帧导入再编码（去掉出怪池后），也只有 184/480 帧（38%）一致，说明翻译层与导入器本身就有损失，不全是 C#/Rust 规则差异。

规则层面的逐步对拍（`combat_diff.py --specs`，用快照题按 C# 随机打法逐步比规范化状态）第一次因为交付包缺 `engine/catalog/v0.111.0/catalog.json` 没跑起来，补上后用户叫停，没有重跑。

## 四、搜索的胜率与耗时

结果见结论第 3 条。补充：

- **打到第二场**：重放 476、导入 476、贪心 470；两种搜索都多赢了一点第一个 Boss。
- **按第一个 Boss**：永世沙漏 127 / 126 对 121（重放 / 导入对贪心，共 168 题）；女王 130 / 130 对 129（155 题）；实验体 145 / 144 对 145（170 题）。
- **改选**：重放每题改选 4.3 次（搜索步的 12.2%），导入 10.5 次（15.9%）；10-31 的 C# 搜索约 9.4 次（11.6%）。导入接法改得最多、赢得最少，与它推演局面最不准一致。
- **不显著的程度**：只有一边赢的题占 5.5%（重放）、7.9%（导入），要以 80% 的把握分清 +1 个百分点，约需 4,300 和 6,200 题，现有题量做不到；如果真实收益有 +3 个百分点，这 493 题看出来的把握约 82%（重放）和 66%（导入）。
- **单步搜索耗时**：没有单独测。全量运行里，每次搜索的墙钟中位约 1.3–1.4 秒、p95 约 1.6–1.7 秒，但那是 12 个分片同时跑、每个分片同时做 2 题、GPU 与采集共用时的数，不是单次延迟。按算法估：每次搜索 2 轮、每轮约 13 次串行网络前向，GPU 上的下限约 0.15–0.3 秒；在直播用的 CPU 推理上会更慢。直播 300–500 毫秒的预算能不能做到，需要单独测。

## 五、能不能用到直播

不能，至少现在不能：

- 直播没有种子，只能走导入接法；导入接法在 C# 帧上只有 2% 的局面对得上，丢了双 Boss 的场次信息和开局选牌；
- 即使在离线、真实结果由 C# 裁判的条件下，导入搜索也只有 +1.0 ± 1.3（不显著）；
- 之前直播的树搜索修好后显著劣于贪心（决策记录 219），说明在不准的推演上搜得越深，越可能把模型往错的方向推；
- 延迟没有验证。

## 六、建议（等修引擎时参考）

按对这次测试的影响排序：

1. **战斗模式的连打与快照**：头部 17、25（双 Boss），以及快照里卡牌的 TINKER、REPLAY 等修正的导入；对照真实快照题开局就不一致的 446 题逐类修。
2. **规则对拍改用真实快照题**：`combat_diff.py --specs 题.json`（交付包要补 `engine/catalog/v0.111.0/catalog.json`），不只看随机牌组；结论按“第一处分歧前走了多少步”和“开局一致的比例”报，而不是只在一致的步上比帧。
3. **导入接法**：带上双 Boss 的场次与第二个 Boss、开局的选牌、能力显示数；战斗模式的帧不要加出怪池记录。先把“Rust 自己的帧导入再编码”做到 100%。
4. **交付包能独立编译**：现在依赖包外的 `engine/catalog/vocab.txt`（`include_str!` 的相对路径）与 catalog，翻译层也在包外的 `.worktrees/main`。
5. **修完重测**：用同一套工具（`tools/pimc_rust_eval.py --arms greedy,rs,imp,cs`）在同一批题上重跑，这次加上 C# 推演对照臂（同题同模型），再单独测单次搜索延迟（`--live 1`，GPU 与 CPU 各一次）。
