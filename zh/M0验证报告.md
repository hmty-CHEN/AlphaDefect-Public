# M0 原型验证报告（2026-10-24）

结论：**在 Linux 的 .NET 9 里直接运行游戏自带的 `sts2.dll` 可行。** 五个角色都能在 A10 下无头开局、走完 Neow 事件、在地图上移动、打完第一场战斗（含敌人回合和多敌人）。结果确定，速度远超预期。技术路线第三节的方案成立，不需要启用退路（Windows 宿主或 Godot `--headless`）。

## 一、环境

| 项目 | 值 |
|---|---|
| 游戏版本 | v0.107.1（提交 `59260271`），Godot 4.5.1，.NET 9 |
| 宿主 | WSL Ubuntu，.NET SDK 9.0.319（装在 `~/.dotnet`） |
| 游戏文件 | 程序集复制到 `~/.local/share/sls2/game/v0.107.1/`；本地化从 pck 提取到同目录下 `res/`（`tools/extract_pck.py`） |
| 反编译代码 | `~/.local/share/sls2/decompiled/v0.107.1/`（ilspycmd 9.1，仅本地查阅，不入库） |
| 模组 | 游戏 `mods/` 下 11 个模组已全部移到 `mods_disabled/`；宿主在测试模式下本来就不加载任何模组 |

## 二、做法

宿主是一个普通的 .NET 控制台程序（`engine/Sts2Headless`），编译时引用游戏的 `sts2.dll`、`GodotSharp.dll`、`0Harmony.dll`，运行时从游戏目录加载。启动顺序照搬游戏的 `OneTimeInitialization`，去掉图集和界面部分，并打开游戏自带的 `TestMode`。

游戏开发者自己的单元测试就在没有 Godot 的情况下跑逻辑，代码里有约 400 处 `TestMode` / `NonInteractiveMode` 分支，动画等待、特效、存档上报在这两种模式下大多已经跳过。剩下的缺口用四类补丁补齐：

| 类别 | 内容 | 对游戏更新的适应性 |
|---|---|---|
| 原生陷阱表 | 用一张函数指针表初始化 GodotSharp，225 个原生入口都指向同一个陷阱函数；被调用时打印完整托管调用栈后退出 | 与游戏代码无关。新增的 Godot 调用会立刻暴露位置，不会静默崩溃 |
| Godot 接口替身 | `GD.Print*`、`OS.*`、`Engine.*`、`Time.*`、`ResourceLoader`（一律不存在）、路径与目录、`Callable.CallDeferred`（排到消息泵）、`StringName`/`NodePath` 构造（空占位） | 只打在 GodotSharp 的公开接口上，游戏更新通常不影响 |
| 自动生成的补丁 | 扫描 `sts2.dll` 的 IL：① 逻辑层调用的界面层静态方法（292 个）统一置空；② 22 处“读帧耗时决定是否插入动画等待”的表达式替换为常数 | 按调用关系匹配，不按方法名。游戏新增的同类代码会被自动覆盖 |
| 点名补丁 | 命令行参数、崩溃上报、存档写盘、回放写盘、本地化文件读取、语言切换通知 | 共 6 组，目标方法消失时启动即报错 |

异步：游戏逻辑大量使用 `async`。宿主把一个单线程同步上下文（`Pump`）挂在主线程上，所有续延都回到同一线程按顺序执行；队列清空就说明游戏在等玩家输入。最初只在推进时临时挂上，敌人回合的续延被投到线程池，结果战斗卡住；改为永久挂上后问题消失，`ForeignPosts` 计数为 0。

玩家选择：
- 战斗内的出牌、药水、结束回合，以及地图选路、事件选项，都调用界面本来使用的逻辑层入口（`TryManualPlay`、`EnqueueManualUse`、`EndPlayerTurnAction`、`VoteForMapCoordAction`、`EventSynchronizer.ChooseLocalOption`）。
- 所有选牌界面在测试模式下都调用 `ICardSelector`，它是异步接口。宿主的实现返回一个挂起的任务，形成决策点，由外部决定后再继续（`AgentCardSelector`）。

## 三、结果

### 3.1 功能

- 五个角色各 60 局，A10，随机合法动作，从开局打到第一场战斗结束，**无一卡住、无未接管的原生调用**。
- 覆盖了单敌人（38 局）、两个敌人（18 局）、三个敌人（4 局）的战斗。
- Neow 的选项中，有的会给卡牌奖励，有的会触发选牌，都能正常走通。

### 3.2 确定性

同一角色、种子、随机策略种子，连跑两次的决策序列和结果完全一致；换种子则不同。三个独立进程的运行指纹也完全相同（`E0770F32…`）。

### 3.3 速度（单进程单线程，A10，随机策略）

| 角色 | 战斗耗时中位 | 每个动作 |
|---|---|---|
| Ironclad | 10.3 ms | 0.59 ms（含首局 JIT 预热） |
| Silent | 5.3 ms | 0.23 ms |
| Defect | 3.2 ms | 0.22 ms |
| Regent | 4.2 ms | 0.20 ms |
| Necrobinder | 5.0 ms | 0.22 ms |

- 进程启动约 1.7 秒（其中 IL 扫描约 1.3 秒，可以缓存）。
- 300 局总耗时约 24 秒，**平均每局约 80 毫秒，其中战斗只占约 5 毫秒**，其余是开局（生成地图、遗物池等）、Neow 事件和清理。
- 单进程峰值内存约 230 MB。

按每个动作约 0.2–0.3 毫秒算，单核每秒 3000–5000 个动作，16 核约 5–8 万个动作/秒。这比技术路线第十二节估计的网络推理吞吐（本机 CPU 上 S 规模约 2000 决策/秒）高一个数量级。**规则模拟不是瓶颈，网络推理和学习才是**，第十二节“以显卡为主”的租机判断得到印证。

## 四、尚未完成（移入 M1）

1. **状态复制**：还没试深拷贝。由于结果是确定的，“从战斗开始按动作前缀重放”已经可用；但开局成本约 75 毫秒，需要先把战斗开局做成可直接构造（战斗课程本来就需要）。深拷贝放到 M1 评估。
2. **卡牌奖励**：游戏的 `GetSelectedCardReward` 是同步接口，目前只能立刻返回，还不能挂起成决策点。M1 需要换成挂起式。
3. **其余房间与界面**：战后奖励、商店、休息处、宝箱、Boss 遗物、事件的多页选项，以及整局结束，都还没走通。
4. **开局提速**：开局每局约 75 毫秒，主要花在什么地方还没剖析。悬浮提示的文本格式化（SmartFormat）在逻辑中被大量即时调用，是首要怀疑对象。
5. **对拍**：还没有和正式游戏对拍。游戏自带战斗回放写入（`CombatReplayWriter`，含校验和），可以用来做对拍。
