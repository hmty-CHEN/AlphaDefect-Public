# PIMC 推理侧提速：测量与结论

日期：2026-11-16。分支 `pimc-infer`（工作树 `~/dev/sls2-infer113`，从 `engine-clone-v0.113.1` 的 9209e29 分出）。
模型：L1000（愚者 v22975 合成滑动平均，格式 27，d 256、6 层）。题目：`tools/future/boss_pimc.py` 的第三幕双 Boss 题 t1（812 题）。
机器：C（3090、i9-14900K 32 线程；P 核为 CPU 0–15，其中 8–11 最高 6.0 GHz，E 核为 16–31）。B 在练愚者，没有用。
代码：`python/sts2rl/infer.py`（推理入口与共用推理进程）、`PolicyValueNet.forward_infer`、`tools/sim_pimc.py` 的 `make_evaluator` / `RemoteEvaluator`、
测量工具 `tools/pimc_infer.py`。没有改 `boss_pimc.py`，测试都是借它的 `Runner`、只换评估器。

## 结论

1. **在 C 上 16 分片 × 8 推演进程（同 B 上测试一的配置）跑满时，推理侧怎么改，整机吞吐都在 3,000 帧/秒左右，没有提速。**
   改前 2,999 帧/秒；一个共用推理进程 3,028；两个 3,025。单次搜索平均 1,652 → 1,605 / 1,638 毫秒。
   原因：这时整机 CPU 被引擎吃满，推理占每题时间的 28%，而每次推理的耗时主要是 Python 逐个算子下发的开销，被争 CPU 放大了 3–5 倍。
   把各分片的小批合到一个进程里，只是把 16 份并行的下发开销换成 1 份串行的，单批变大，但单批的下发也被拖慢，两者抵消。
2. **共用推理进程的实际收益是显存和部署**：显存 7.4 GB → 约 0.8 GB（16 个显卡上下文 → 1 个），模型只载一次。
   B 在训练时显存只剩 0.7–3.3 GB（学习端在 21.2–23.8 GB 之间涨落），“16 分片各载一份”根本跑不起来，共用推理进程是这种情况下唯一能用显卡推理的办法。
3. **共用推理进程 fp32 完全复现原路径的搜索结论。** 逐根双跑（同一个根、同样的世界种子各搜一遍，20 题 1,333 个根）：
   同一（候选、种子）的 36,036 个世界得分全部相同；最终动作逐字相同 96.77%，加上“结局等价”（两边选的两个动作在每个世界里得分都相同）为 99.92%，
   剩下 1 个是逐轮减半时两个候选第一轮平均分相同、按根概率打破并列。原路径自己再搜一遍（噪声底，21 题 1,158 个根）是 96.72% / 99.91%，同样剩 1 个同类并列。
   两臂在同一局面上的对比（A 对 B1、B2，2,338 / 2,568 个根）是 96.6% / 96.9%，加上结局等价 99.91% / 99.96%。胜率没有看到下降（配对 31 → 30、31 → 31，样本小）。
4. **精度保持 fp32。** fp16 真正改变了约 2% 的决策（21 题 1,511 个根，结局等价也算上只有 98.15%，24% 的世界得分变了）；bf16、CPU int8 偏差更大
   （对数几率最大差 1.6 和 3.0），排除。fp16 / TF32 只在单批 128 帧以上快约 25%，在线时每批只有约 30 帧、瓶颈不在显卡算力，拿不到这部分收益。
   另外发现 **boss_pimc 的改选判据没有最小效应量**：两个动作结局相同时标准误为 0，平均差只剩 ±1e-8 的浮点噪声，`m > z·se` 就看噪声的正负，
   约 3% 的搜索根是这样选出来的（双跑里 1,333 个根中 42 个，同局面对比里 2,338 个中 78 个）。逐轮减半按根概率打破平均分并列，也是同一类问题。对棋力无影响（两个动作结局相同），但让每次重跑的轨迹不同；要可复现，判据可以加一个最小差（例如 m > max(z·se, 1e-4)），这次没有改。
5. **下一步真正能降推理耗时的是 CUDA Graphs**（按形状分桶、补齐到固定形状），把每批约 3 毫秒的下发开销降到零点几毫秒；
   引擎复制让引擎快 2–3 倍之后，推理占比会从 28% 升到一半左右，那时这一步才值得做。本次没有做，理由与估算见第七节。

## 一、改了什么

- `PolicyValueNet.forward_infer`（提交 b46c400）：只算策略与价值，不算牌组打分和辅助头，`hl_beta` 为 0 时跳过分类价值头。
  与 `forward` 逐位相同；`forward_all` 拆成三段，训练路径的运算与顺序不变（旧、新 `forward_all` 在 226 批上 `torch.equal` 逐位相同）。
- `sts2rl.infer.InferEngine`：`inference_mode` + `forward_infer`，可选 TF32 / fp16 / bf16（autocast）、CPU int8 动态量化、线程数、
  `torch.compile`、打包注意力、整批一次拷到显卡。
- `sts2rl.infer.serve` / `InferClient`：Unix 套接字上的共用推理进程，凑批规则同训练采集的 `infer_wait_ms`：
  所有已连接的客户端都在等，或等满 `wait_ms`（默认 2 毫秒），或凑满 `max_rows`，就合成一批。回复按请求拆开，宽度与单独前向时相同。
  推理进程收到的输入与本地同批前向逐位相同（CPU 上核对，深度 1、2 都是）。
- `tools/sim_pimc.py`：`ModelEvaluator` 默认行为不变（仍是 `net(batch)` + `no_grad`，直播的代理照常能用）；
  加 `make_evaluator(spec, …)` 与 `RemoteEvaluator`。新旧 `ModelEvaluator` 在 200 个根帧上输出逐位相同。
- `tools/pimc_infer.py`：`record`（录推演帧）、`diff`（同一批帧上的偏差）、`bench`（单进程测速）、`serve`、`load`（多客户端压测）、
  `play`（照 boss_pimc 打题、换推理路径）、`agree`（逐根双跑）、`report`、`agree-report`。

## 二、同一批帧上与 fp32 的差别（C，3090）

输入：在 C 上用原路径跑 4 题录下的帧（`record`），共 7,636 批 57,232 个推演帧（每批平均 7.5 帧）与 420 个根帧；对照用前 2,000 批（14,310 帧，其中 12,912 帧要出手）。
参照是原路径（`net(batch)`、fp32、原来的批）。“翻转”是要出手的帧上最高项变了；原路径里两项本就逐位相同（同样的两张牌）只是并列时换了下标的，不算。

| 路径 | 翻转 | Δ对数几率 p99 / 最大 | Δ价值 最大 |
|---|---|---|---|
| 原路径再跑一次，同样的批 | 0 | 2.1e-5 / 1.2e-4 | 1.6e-6 |
| fp32 新路径，同样的批 | 0 | 2.1e-5 / 9.7e-5 | 1.5e-6 |
| fp32 新路径，重切成每批 128 帧 | 0 | 4.0e-5 / 2.6e-4 | 2.0e-6 |
| fp32 + `torch.compile`（前 600 批） | 0 | 1.9e-5 / 6.5e-5 | 7.8e-7 |
| TF32 | 2–3（另 1 次并列） | 0.034 / 0.17 | 0.0023 |
| fp16 | 4–5（另 0–1 次并列） | 0.078 / 0.23 | 0.0080 |
| bf16 | 82–83（0.6%） | 0.64 / 1.63 | 0.10 |

- 原路径在显卡上本身就不逐位可复现（`index_add_` 在显卡上是原子加，求和顺序不定），量级 1e-4；fp32 新路径、换批大小、compile 都在这个量级。
- TF32 / fp16 翻转的帧，原路径上前两名只差 0.004–0.016；bf16 的差到 0.08，而且价值差 0.1，与候选之间的配对差同一量级。
- 打包注意力（`fast`）的偏差与对应精度的分组路径相同，但慢得多（见下节）。

## 三、单进程测速（C 空载，3090）

每批 B 帧，组批（numpy）+ 前向（含拷到显卡、拷回），40 批平均：

| 路径 | B=8 前向 | B=32 前向 | B=128 前向 | B=128 组批 | B=128 帧/秒 |
|---|---|---|---|---|---|
| 原路径 | 3.30 毫秒 | 3.50 | 6.13 | 1.14 | 17,599 |
| fp32 新路径 | 2.80 | 3.12 | 5.88 | 1.16 | 18,168 |
| fp32，逐个数组拷到显卡 | 2.86 | 3.14 | 5.81 | 1.17 | 18,332 |
| TF32 | 2.81 | 2.91 | 4.58 | 1.14 | 22,374 |
| fp16 | 3.77 | 3.90 | 4.44 | 1.13 | 23,000 |
| bf16 | 3.66 | 3.77 | 4.42 | 1.13 | 23,066 |
| 打包注意力 fp32 | 11.25 | 11.40 | 12.63 | 1.17 | 9,271 |

- 小批时前向几乎是常数（B=1 也要 2.7 毫秒），这是逐个算子下发的开销；B 从 8 到 128，帧/秒涨 8 倍。
- `forward_infer` + `inference_mode` 让小批快约 15%（3.30 → 2.80 毫秒）。整批一次拷到显卡没有可测的收益。
- 半精度只在大批上有用；小批反而更慢：autocast 多了类型转换的算子，而且关掉了编码器层的融合快速路径。
- 打包注意力（嵌套张量 SDPA）在推理的批大小上固定 11 毫秒以上，放弃。
- `torch.compile(dynamic=True)`（空载，两轮交替）：B=8 前向 3.15 毫秒对 eager 2.83–2.97，B=32 3.23 对 3.19–3.31，B=128 5.72 对 5.94–5.96，最多快 4%，小批反而慢；数值与原路径等价。

## 六、改选决策与 fp32 一致的比例

两种口径：

1. **两臂在同一局面上**（`report`）：两臂标签里根帧逐字节相同的根，比最终选的动作。
2. **逐根双跑**（`agree`）：实机照原路径走；每个要决策的根上，新路径用自己的根概率决定搜不搜，搜就用同样的世界种子再跑一遍，比两边最终选的动作。
   “噪声底”一组的新路径就是原路径本身（同一进程里再搜一遍），量的是显卡浮点不定序带来的差别。三组同时在 C 上跑 15 分钟，分片 0–4 / 5–9 / 10–15，各自打不同的题。

“结局等价”：两边选的动作不同，但参照的搜索里这两个候选在每个共同世界的得分都相同（差 ≤ 1e-3）。原因见结论第 4 条：判据 `m > z·se` 在两个候选结局相同时只看浮点噪声的正负。

| 对照 | 题 | 根 | 最终动作逐字相同 | 加上结局等价（95% 区间） | 同一世界得分不同 | 另：贪心项不同 / 门限两侧 |
|---|---|---|---|---|---|---|
| 原路径对自己（噪声底） | 21 | 1,158 | 96.72% | 99.91%（99.51–99.98%） | 0.0%（31,736 个世界） | 0 / 0 |
| 共用推理进程 fp32 | 20 | 1,333 | 96.77% | 99.92%（99.58–99.99%） | 0.0%（36,036） | 0 / 0 |
| 共用推理进程 fp16 | 21 | 1,511 | 94.90% | 98.15%（97.33–98.71%） | 24.0%（40,484，平均差 0.001） | 5 / 2 |
| 两臂同局面：A 对 B1（共用 1 个） | 38 | 2,338 | 96.58% | 99.91% | — | — |
| 两臂同局面：A 对 B2（共用 2 个） | 37 | 2,568 | 96.88% | 99.96% | — | — |

噪声底与 fp32 各剩 1 个不一致：逐轮减半时两个候选第一轮平均分相同，按根概率（两边差 1e-6）打破并列，进第二轮的候选不同。

- fp32 与噪声底没有区别：世界得分全部相同，逐字不同的根除各 1 个减半并列外全是结局等价。
- fp16 有 24% 的世界得分变了（叶子估值差千分之几、或推演中途某步最高项翻转后整条走岔），去掉结局等价后仍有约 2% 的根选了真正不同的动作。
- 不一致的根并不集中在门限附近：A 对 B1 中，不一致的根离门限（(m − 2se) / se 的最大值）的中位距离是 2.0 个标准误，一致的根是 1.8，
  这是因为不一致几乎全是上面那种标准误为 0 的结局等价，不是“差一点就过门限”。

## 七、没有做的与放弃的

- **CUDA Graphs**：要把一批的所有不定长下标（记录、候选、能力、招式、汇总槽、特权等十几种）补齐到分桶后的固定长度，
  `_split` 的 `nonzero` 也要改成按行选择，等于另写一份固定形状的前向。按上面的数字估：每批下发约 3 毫秒（空载）可降到零点几毫秒，
  B1 里每批 6.3 毫秒的处理可降到约 2 毫秒，每次推理 11.6 → 约 5 毫秒，在 C 现在的配置下每题省约 15%。
  引擎复制让引擎快 2–3 倍后推理占比会到一半左右，收益随之变大。开发要在显卡上调，本次 C 要让给引擎复制会话，没有做。
- **`torch.compile`**：数值与原路径等价，但空载时最多快 4%、小批更慢（第三节），不用。它不改变逐算子下发的结构（形状不固定、`nonzero` 处断图），省不掉主要开销。
- **流水深度 2**（组批与前向分两个线程）：Python 两线程抢 GIL，在线反而变慢（B0），保留选项但默认 1。
- **CPU int8**：见第八节，偏差太大。
- **整批一次拷到显卡**：没有可测收益，但数值相同，保留为默认。

## 八、CPU 推理（直播、本机）

本机 i5-12600KF（AVX2，无 AVX-512 / AMX），测量时其他会话把负载推到 10–40，速度只作相对参考；偏差与负载无关。
输入为本机录的 2 题（2,875 批 21,927 帧），对照前 1,200 批（8,714 帧，其中 8,000 帧要出手），参照为原路径 8 线程。

| 路径 | 翻转（不含并列） | Δ对数几率 最大 | Δ价值 最大 | B=8 前向 | B=32 前向 |
|---|---|---|---|---|---|
| fp32 8 线程 | 0 | 0 | 0 | 25.4 毫秒 | 80.7 |
| fp32 4 线程 | 1（前两名差 1e-5），另并列 5 | 1.2e-4 | 1.3e-6 | 26.8 | 72.8 |
| fp32 2 线程 | 1（差 1e-5），另并列 7 | 1.4e-4 | 1.3e-6 | 32.2 | 85.9 |
| fp32 1 线程 | 1（差 1e-5），另并列 5 | 1.0e-4 | 1.7e-6 | 40.6 | 131.4 |
| int8 4 线程 | 153（1.9%） | 3.0 | 0.14 | 20.3 | 55.5 |

- 换线程数只改变 GEMM 的分块与求和顺序，差 1e-4，只在前两名差 1e-5 的帧上换了最高项；4 线程与 8 线程一样快，机器忙时线程多反而更慢
  （负载 25–40 时同一批帧 8 线程 67 秒、4 线程 3.7 秒）。直播或本机 CPU 推理建议 `threads=4`。
- int8 动态量化（只量化编码器前馈两层与候选、价值头）快约 25%，但翻转 1.9%、价值差 0.14，不能用在搜索上。

## 九、接到 boss_pimc（等引擎复制合并到 engine-clone-v0.113.1 之后）

`Runner.__init__` 里把评估器换成工厂（加一个 `--infer` 参数，默认空即原路径）：

```python
self.ev = X.make_evaluator(a.infer, self.net, a.device, policy_mode=MODE_COMBAT, value_mode=MODE_COMBAT, strip_priv=True)
```

用共用推理进程时分片给 `--device cpu`（不建显卡上下文；`unix:` 时 `net` 不用，可以跳过载入）。`--residual` 是挂在本地网络上的钩子，共用推理进程里没有，需要的话给 `serve` 加同样的挂法。
异步凑批（`--async`）照样能用：`RemoteEvaluator.rollout` 与原来的接口相同，跨分片的合批在推理进程里做。

起推理进程（C 上的做法；B 上按它的核编号选一个空闲的快核，并先看显存：推理进程约 0.7 GB，训练时 B 只剩 0.7–3.3 GB）：

```bash
OMP_NUM_THREADS=1 nice -n -10 taskset -c 8,9 .venv/bin/python -I tools/pimc_infer.py serve --ckpt L1000.pt --ema --device cuda --ev fp32 --sock /tmp/pimc.sock --wait-ms 2 --depth 1
```

分片：`taskset -c 0-7,10-31 … boss_pimc.py run … --device cpu`，评估器用 `unix:/tmp/pimc.sock`。
