# 局面复制无头引擎报告（2026-11-16）

用户要求：在 sls2 项目里做一个能“复制局面”的无头引擎，对应游戏 v0.113.1，易于维护、能跟随游戏版本更新。具体三件事：

1. 测清现在的推演成本；
2. 按《引擎模块与游戏更新适配》把引擎适配到 v0.113.1；
3. 加局面复制，调研路线后再做。

开发中途用户追加：“引擎最好考虑到我们的训练和搜索需求进行专项的优化”，审阅优化点后“全都做”。

分支 `engine-clone-v0.113.1`（从 `game-v0.113.0` 的 e41ea1d 分出），工作目录 `~/dev/sls2-clone113`。**训练的部署没动**：愚者训练仍跑 v0.113.0，切不切由用户定。

## 摘要

- **v0.113.1 适配**：引擎代码不用改。自检时兼容层 144 处全部找到，词表新增 0 项。新旧引擎逐字节对拍 9,194 帧，0 处不同。
- **局面复制**：进程内原地快照，在 `engine/Sts2Headless/Engine/Clone/`，设计与维护写在同目录的 `局面复制.md`。
  - 协议：`snapshot` / `restore` / `drop`；任何返回帧的请求都可带 `"snapshot":k`，推演进程跟随根局面时用它。
  - 速度（C 机空闲）：拍快照约 1.0–1.3 ms，恢复约 0.1 ms。
- **保真**：跨进程比较“复制后接着走”与“重放到这里再走”，战斗练习约 10 万帧、整局约 2.6 万帧，0 处不同。分叉点覆盖已知牌堆顶、恢复前开过别的局、嵌套快照、整局的各类决策。
- **不用复制时行为不变**：
  - random 200、starter 200 对拍，0 处不同；
  - `engine_equal` 16,253 帧，0 处不同（提速子智能体另测 46,130 帧，0 处不同）；
  - 实机导入保真 99.891%，与原版逐局相同。
- **速度**（C 机，RTX 3090，32 核，16 分片 × 8 进程满载，GPU 推理）：
  - 一次 PIMC 搜索 1,506 → 639 ms，**2.36 倍**；每个世界的引擎开销约 103 → 22 ms，4.7 倍。
  - 整局模式（直播那种从第一层重放），第三幕 Boss 处每个世界的起步 167 → 2.0 ms，**84 倍**。
- **专项优化**：编码观测每帧 3.3 → 0.9 ms；`auto_single`（单候选的决策由引擎走过）；`keep_top`（reseed 保留已知牌堆顶）；训练用的 `Sts2Env.snapshot/restore/drop`。
  - 范围化快照、GC 参数：测过，不值得或没有收益，没做。
- **另两件事**：
  - 推理侧（共享推理进程、半精度）交给了另一个会话，在分支 `pimc-infer`，已按用户决定接进本分支（`boss_pimc --infer`）；
    满载时共用推理进程比各分片自带 GPU 慢约 19%，价值在省显存（第七节）；
  - 验收中发现直播无头搜索的镜像有潜伏的失步问题（第八节）。

## 一、现在的成本（基线）

两处测量，口径相同：`tools/future/boss_pimc.py`，第三幕双 Boss 题（`items_t1.json`），L1000 滑动平均，PIMC 参数同愚者决策记录第 25 条，`STS2_TIMING=1` 取引擎分项。

**本机**（6 个推演进程，CPU 推理，4 题 200 次搜索）：每次搜索平均 2,032 ms。每个世界的引擎开销：

| 项 | 耗时 |
|---|---|
| reset | 4.6–5.4 ms |
| replay（含 reseed 与首步） | 61–69 ms |
| 往下每步：step / 取决策 / 编码 | 1.1 / 0.26 / 4.1 ms，约 11 步 |

合计约 128 ms，其中重放占一半，编码占四成。

**C 机**（16 分片 × 8 进程，CPU 吃满，GPU 推理，32 题）：原版引擎每次搜索平均 1,506 ms。每个世界 reset 4.4 ms + replay 49.8 ms，每步 step 0.74 / 取决策 0.21 / 编码 3.52 ms。

用户在 B 上看到的 2.3 秒，与 C 上的 1.5 秒是同一种满载条件，只是机器不同。B 在跑愚者训练，没有拿来测速。

## 三、局面复制

调研了六条路线（`局面复制.md` 第二节）：

- **游戏存档**：不含战斗中途状态。
- **fork**：.NET 进程 fork 后子进程段错误，实验验证。
- **手写序列化**：难维护。
- **深拷贝成新对象**：要改指向的地方太多。

所以选了**原地快照**：从静态根出发，浅拷贝每个可变对象，恢复时把字段原地写回。对象身份不变，字典、闭包、挂起的异步状态机都不用重建。逐字段的读写代码按类型用 IL 生成，不需要为每种游戏对象写代码。

游戏更新时要复核的只有两个文件：`ClonePolicy.cs`（哪些类型当叶子、哪些静态字段是根）和 `TypeInit.cs`（运行时内部布局，第一次使用前会自动核对）。游戏规则本身的变化不用管。维护步骤已写进 `局面复制.md` 第六节与《引擎模块与游戏更新适配》第六节第 10 步。

### 开发中查出并修好的问题

1. **`WeakReference` 被浅拷贝**：快照丢掉后，拷贝的终结器释放了和原对象共用的句柄，正则的替换缓存随即空引用。修法：带终结器的对象拷贝后取消终结；弱引用当叶子。
2. **“已知牌堆顶”漏记**：引擎记已知牌堆顶用的弱引用表最初被当成叶子，恢复后留着死去那条时间线的值。
   - 随机局里这种局面一次都没出现，往返测试测不出来；
   - 构造专放牌堆顶的牌组后，80 局里 35 局报不同；
   - 修法：弱引用表按键值对存取，只存键在别处也走得到的条目（否则 GC 还没回收的旧战斗会被拖进来，每份快照从约 2,500 个对象涨到 65,000 个）；
   - 留了反向核对开关 `STS2_CLONE_WEAK_LEAF=1`，用来证明测试抓得住这类问题。
3. **钩子监听者列表池放在线程静态字段里**：这是提速子智能体自己查出来的。池不进快照，在“钩子迭代停在等玩家选牌”的决策点拍快照、恢复后，同一个列表被两处共用，18 题全部卡住。改成普通静态字段后，池随快照一起恢复。`clone-test census` 现在会列出全部线程静态字段，供维护时逐个确认。
4. **引擎自己的类型晚初始化**：整局里第一场战斗前拍的快照没有 `Observation.DrawTop` 的静态字段。分析下来残留条目查不到、没有造成不同，但不该靠巧合。现在第一次拍快照时先初始化全部引擎类型（`selfcheck` 一直在这样做）。
5. **漏记审计自身的问题**：一处是反射读受限字段时报错，改为 IL 比较器；另一处是惰性缓存的标记里含全角冒号，按冒号切分时误判为不通过。

### 失败与放弃的尝试

- **主动初始化所有游戏类型**：一些非界面类（`RichTextUtil` 等）的静态初始化会调 Godot 原生接口，无头下进程直接退出（退出码 97），按规则排除不完。改成只取已经初始化的类型，晚初始化的记进清单。v0.113.1 测到的晚初始化类型只有常量表、界面缓存、编译器生成的委托缓存和测试注入钩子，逐个看过。
- **范围化快照**（只写回战斗中会变的对象）：走 12–40 步后被改过的对象只占 3.6–4.0%，最多省约 0.3 ms，不到每个世界开销的 0.5%，还有漏记风险。只做了测量。
- **GC 参数**：在 C 机空闲时测了两轮，默认设置最好。不改。
- **dotnet-trace 采样剖析**：偏差大，显示列表扩容占 77%，实测只有约 5%。提速子智能体改用计次加开关对照来定位。

## 四、专项优化

### 编码观测与 step（子智能体甲，9 笔提交）

- 一次编码之内的记忆化，每帧 ×0.44。记的是同一帧里反复问游戏的数值预览、打出次数、关键字、能否打出、费用、可攻击的敌人。
- 编码期间冻结钩子监听者序列，×0.63。
- 旋律是否打出过只问一遍，×0.89。
- 怪物意图伤害的记忆、帧缓冲预分配、反射读取改成委托，×0.94。
- 钩子监听者列表复用、`Slugify` 结果缓存。

合计每帧 3.3 → 0.9 ms，各格式（19、22、23、27）都降到 0.8–0.9 ms。`step` 的稳态没变：游戏逻辑之外的开销本来就很小。

每笔都在同一进程里开关对照、逐字节比对；最终对参照引擎 46,130 帧，0 处不同。

### 搜索与训练用的接口

- **`auto_single`**：单候选的决策由引擎自己走过，不编码、不回 Python。可带整数上限，保证“走 12 步后估值”的那一帧与逐步走相同。
- **`keep_top`**：reseed 时不洗已知的抽牌堆顶，解决直播接入.md 写的已知局限。它会改变推演世界的分布，开不开由使用者定。
- **`restore` 只带 `first`** 时也走这一步。
- **Python**：`Sts2Env.snapshot / restore / drop`，示例 `tools/clone/env_fork_demo.py`：在决策点分出推演、推完恢复、接着走，215 条推演与不分叉的进程 0 处不同。
- **boss_pimc** 的开关，默认全关、行为不变：
  - `--worlds clone`：推演进程跟随根局面，不再重放；
  - `--async`：异步凑批；
  - `--auto-single`、`--keep-top`、`--warm`；
  - 对照工具 `tools/clone/pimc_compare.py`。

- **复制路径**：走到分叉点 → 拍快照 → 每个世界 restore + reseed + first，再走 K 步；
- **重放路径**：reset + replay + reseed + first，再走同样的 K 步。

逐帧比原始字节，跳过随进程累计的头部 12、14。

## 六、速度

### 端到端：PIMC 搜索

C 机，同一批 32 题，16 分片 × 8 进程满载，GPU 推理：

| 配置 | 每次搜索 平均 / 中位 | 相对原版 | 墙钟 | 胜 / 改选 |
|---|---|---|---|---|
| 原版引擎（v0.113.0，重放） | 1,506 / 1,567 ms | — | 326 秒 | 26 / 275 |
| 最终构建，只用重放（编码提速） | 1,093 / 1,110 ms | 1.38 倍 | 245 秒 | 25 / 272 |
| **最终构建 + 复制** | **639 / 637 ms** | **2.36 倍** | 153 秒 | 26 / 299 |
| 复制 + auto_single | 639 / 636 ms | 2.36 倍 | 156 秒 | 26 / 289 |
| 复制 + auto_single + 异步凑批 | 689 / 673 ms | 2.19 倍 | 163 秒 | 26 / 294 |

单分片（8 进程，不满载，4 题）：原版 449 / 450 ms，复制 + auto_single 260 / 294 ms，平均快 1.73 倍。

各配置的胜负与改选次数在噪声内一致。复制与重放在规则上完全等价：子智能体乙在固定线程数下核对过，201 次搜索里每个世界的得分逐一相同。差别只来自网络前向的批组成不同带来的浮点误差，大约 6% 的行会在两张相同的牌之间换首选。

引擎分项（满载）：

| | 原版 | 复制后 |
|---|---|---|
| 世界起步 | reset 4.4 + replay 49.8 ms | 恢复 1.4 + 首步 1.2 ms |
| 往下每步 | 编码 3.52 + step 0.74 + 取决策 0.21 ms | 编码 0.84 + step 0.69 + 取决策 0.19 ms |
| 每个世界（按约 11 步） | 约 103 ms | 约 22 ms，**4.7 倍** |
| 其他 | | 每个根拍一次快照：满载约 16 ms，空闲约 1.2 ms |

端到端只有 2.36 倍，是因为剩下的时间主要在 GPU 推理上。同样的原因，满载时 auto_single 和异步凑批没带来额外收益。推理侧的优化由另一个会话完成，见第七节。

### 整局模式（直播那种从第一层重放）

12 局真实直播整局，第三幕第一个 Boss 战第 10 步作根，C 机空闲：

- 每个世界的起步：重放 580–816 步 + reseed + 首步，平均 167 ms（中位 154）；restore + reseed + 首步，平均 2.0 ms（中位 1.7），**84 倍**。
- 加上往下推演 12 步（新编码器约 20 ms），每个世界的引擎开销约快 8 倍。
- 直播里搜索时机器还在跑游戏和别的东西，重放会更慢，倍数只会更大。

### 快照本身

| 条件 | 拍快照 | 恢复 |
|---|---|---|
| C 机空闲，战斗（约 2,400 个对象） | 1.0–1.3 ms | 0.10–0.12 ms |
| C 机空闲，整局（约 3,100 个对象） | 1.3 ms | 0.15 ms |
| 满载（16 分片 × 8 进程） | 16 ms | 1.4 ms |

作为对照，sts2-sim 文档记的是存 0.07–0.09 ms、读 0.13–0.18 ms，两者是同一量级。但 sts2-sim 是 v0.111.0 的移植，没有愚者。

### 与“多一到两个数量级搜索标签”的目标

战斗练习模式里，复制之后剩下的时间几乎都在推演本身：每个世界约 11 步，每步要编码，还要过一次网络。引擎侧已经快了 4.7 倍，端到端 2.4 倍；整局模式的收益大得多。

要再上一个数量级，需要搜索算法层面的改动，比如更少的世界、更短的推演、叶子直接估值，或者用快照做树搜索：中间节点也存快照，子节点从中间节点恢复。这些现在都可以做了，但不在本次范围内。

## 七、并行的工作与分工

- **子智能体甲**（编码与 step 提速）、**子智能体乙**（验收工具、复制版 PIMC、训练接口）：各在独立分支 `engine-clone-perf`、`engine-clone-tools` 上提交，已 cherry-pick 进主分支。两个工作目录 `~/dev/sls2-clone113-perf`、`~/dev/sls2-clone113-tools` 还留着。
- **推理侧会话**：共享推理进程、半精度，用户交给另一个会话做。
  - 交付在分支 `pimc-infer`，报告 `reports/PIMC推理侧提速.md`；
  - 它的速记：C 上满载时共享推理进程 fp32 与改前吞吐持平（每秒 3,028 对 2,999 帧），显存 7.4 → 0.8 GB，搜索结论一致；
  - 用户决定接进来：它的 4 个提交已 cherry-pick 进本分支，boss_pimc 加了 `--infer`（默认空，原路径不变；`fp32` 为推理专用前向；`unix:套接字` 为共用推理进程，分片不载网络）。
  - 本机冒烟（复制版世界、CPU 推理、第 0 题）：三种推理路径逐个世界的读数 37/37 全同，改选全同。
  - **接上复制引擎后的实测**（C 机，16 分片 × 8 进程满载，复制 + auto_single，同一批 32 题）：

    | 推理方式 | 每次搜索 平均 / 中位 | 墙钟 | 胜 |
    |---|---|---|---|
    | 各分片自带 GPU（两轮） | 639 / 636 ms；636 / 632 ms | 156 / 150 秒 | 26 |
    | 共用推理进程（GPU，钉 8、9 号核；分片用 CPU、钉其余核） | 758 / 801 ms | 177 秒 | 26 |

    引擎变快后，共用推理进程在满载时慢约 19%：分片少了两个核，各分片的推理都排到一个进程里串行下发。
    它的价值仍是显存（7.4 → 0.8 GB）：B 在训练时显卡只剩 0.7–3.3 GB，“每个分片各载一份”放不下，那时只能用它。
    **建议**：显存够时用默认路径（各分片自带 GPU）；显存紧时（B 训练期间）用 `--infer unix:`。
- **机器**：
  - B 只做过只读查询，训练没受影响；
  - C 由用户让恐惧训练暂停后借用。先给推理侧会话用，之后我独占测速。我的目录是 `/root/clone-deploy`、`/root/clone-bench`；恐惧线的部署目录、运行目录、STOP 标记、crontab 都没动。

## 八、验收中发现的、不属于本任务的问题

**直播无头搜索的镜像会失步**（`sls2-live113` 的 `python/sts2rl/headless_search.py`，直播会话的文件，没动）。

实机导入保真里，两个分组合计 165 局，有 72 局在某一帧和引擎对不上（v0.113.1 分组 132 局里 57 局），都是编码或界面差异，与规则无关：

- 瓦库事件的访问次数来自本机存档（40 局）；
- 试炼事件的编号来自不带种子的 `Rng.Chaotic`（12 局）；
- 第二幕木偶名的候选文字，实机是中文、引擎是英文（17 局）；
- 五轮书的计数，实机在激活动画中途读到 5（3 局）。

镜像只跳过头部 12，所以这些局会在第三幕 Boss 之前停止搜索：不一致都出现在第二幕或第三幕的事件、地图帧上。直播日志里没见到失步记录，大概是因为这个搜索现在没开。要修，可以屏蔽这几项编码，或者放宽镜像的比较，由用户和直播会话决定。
